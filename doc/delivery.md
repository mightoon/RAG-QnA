完整的交付操作流程：

---

## 整体思路：三阶段交付

```
阶段一：启动服务          阶段二：连接资源          阶段三：注入知识
（让系统跑起来）          （告诉系统去哪找东西）     （把客户数据喂进去）
      ↓                         ↓                         ↓
  docker run               UI 配置 + 保存               上传文档
  看到登录页               健康检查全绿                  触发入库
                                                        等待完成
                                                            ↓
                                                        开始问答
```

---

## 阶段一：启动服务

这一步的目标是让系统进程跑起来，能访问到登录页。**此时系统还不能正常工作**，因为还没连接任何外部资源。

**前提条件**：客户环境需要先独立准备好基础设施——这些不是系统本身，而是系统依赖的外部服务：

```
必须事先准备好的服务（最小集）：
  ├── Redis          ← 存 Session 状态（可用客户现有 Redis）
  ├── Milvus 或 Qdrant  ← 向量库（新建或客户已有）
  ├── Elasticsearch  ← 全文索引（新建或客户已有）
  ├── MinIO 或对象存储  ← 存原始文件（可用本地目录替代）
  └── LLM 推理服务   ← 模型接口（客户私有部署 or 云端 API）
```

这些服务可以是客户环境中已有的，也可以用 `docker-compose.yml`（框架自带）在同一台服务器上一键启动。

启动系统本身只需两步：

```bash
# 第一步：把配置文件放到位（可以先填个空壳，后面 UI 里改）
cp customer_config.yaml.template customer/config/customer_config.yaml

# 第二步：启动
docker run -d \
  -p 8000:8000 \
  -v ./customer:/app/customer \
  -e ABC_LLM_API_KEY=... \
  rag-framework:latest
```

访问 `http://服务器IP:8000`，看到登录页说明服务已启动。

## 阶段二：通过 UI 配置资源连接

接下来"通过 UI 配置客户环境的资源"是正确的，但有一个重要的**先后顺序问题**需要理解清楚。

### 两种配置方式并存

| 方式 | 适用场景 | 谁来操作 |
|------|----------|----------|
| **直接编辑 YAML 文件** | 首次部署，批量配置 | 交付工程师 |
| **UI 配置界面** | 上线后的参数调整 | 管理员 |

**首次部署建议直接编辑 YAML**，而不是全靠 UI，原因是：UI 配置界面本身需要有人登录，而登录需要认证服务已配置好；认证服务又需要 Auth 适配器的配置。这个"先有鸡还是先有蛋"的问题，最简单的破解方式是在 YAML 里先填一个最小配置（JWT 本地认证 + 默认 admin 账号），启动后用默认账号登录，再去 UI 里完善其他配置。

### UI 配置界面的操作流程

登录后进入系统配置页，按以下顺序操作四个 Tab：

**第一步：资源连接 Tab**

逐一填写每类资源的连接信息，填完一个点"测试连接"，看到绿色"连接正常"再填下一个：

```
LLM 服务
  适配器类型: openai_compatible
  服务地址:   https://llm.xxx.com/v1
  API Key:    ****
  默认模型:   qwen2.5-72b-instruct
  [测试连接] → ✓ 连接正常，延迟 234ms

向量库
  适配器: milvus
  地址:   192.168.1.100:19530
  [测试连接] → ✓ 连接正常

全文检索
  适配器: elasticsearch
  地址:   192.168.1.101:9200
  [测试连接] → ✓ 连接正常

知识图谱（如果客户没有）
  enabled: 关闭  ← 直接关掉，不用管它

业务数据库（如果客户有）
  enabled: 开启
  连接串: postgresql://...
  允许查询的表: orders, products, ...
  [测试连接] → ✓ 连接正常
```

**第二步：功能开关 Tab**

根据客户实际资源情况调整，资源没有的路直接关掉：

```
向量语义召回:  ✓ 开启
BM25 关键词召回: ✓ 开启
知识图谱召回:  ✗ 关闭（客户没有图谱库）
结构化数据查询: ✓ 开启（客户有业务数据库）

图片内容理解:  ✓ 开启（客户文档有大量图表）
Cross-Encoder 重排: ✓ 开启
忠实度校验:   ✓ 开启
```

**第三步：知识域权限 Tab**

定义角色和知识域的访问关系：

```
role_admin    → *（所有知识域）
role_rd       → tech_docs, api_docs
role_hr       → hr_docs, policy_docs
role_sales    → product_docs, case_docs
```

**第四步：提示词 Tab**

把 System Prompt 改成符合客户业务语境的描述，例如将"专业智能问答助手"改成"ABC 集团内部知识助手"，并添加 2-3 条意图分类示例帮助模型更准确地分类客户业务场景的问题。

**最后：保存配置**

点击保存后，系统热重载配置（部分参数需要重启服务生效，UI 会提示）。

## 阶段三：注入客户数据

注意：不是把数据直接导入各类数据库，而是把原始文档交给系统，由系统自动完成解析、分块、向量化、写入各库的全过程。

### 文档知识的注入（主要路径）

有两种方式，效果相同，场景不同：

**方式 A：通过 UI 上传**（适合少量文档，或上线后日常维护）

进入"知识库"页面：
1. 右上角选择知识域（collection），如"tech_docs"
2. 拖拽文件到上传区，或点击选择文件（支持 PDF/Word/TXT/图片）
3. 系统自动触发入库流程，进度条实时显示：等待中 → 解析中 → 分块中 → 入库完成
4. 入库完成后文档列表中出现该文档，显示 Chunk 数量

**方式 B：命令行批量入库**（适合首次大批量导入，数百到数千文档）

```bash
# 进入服务器，执行入库脚本
docker exec -it rag-container python scripts/ingest.py \
  --dir /path/to/客户文档目录/ \
  --collection tech_docs \
  --roles role_rd,role_admin \
  --concurrency 4

# 运行过程输出示例：
# 共发现 238 个文件，开始入库（并发数=4）...
#   ✓ 产品手册_X300.pdf → 127 chunks
#   ✓ OSPF配置指南.docx → 43 chunks
#   ✓ 组网方案.pdf → 89 chunks
#   ...
# 入库完成：成功 235 个，失败 3 个，共生成 8421 个 Chunk
```

失败的 3 个文档查看日志，通常是文件损坏或格式不支持，单独处理后重新上传即可。

### 结构化业务数据（补充路径，如果客户有业务数据库）

**系统不会把业务数据库的数据复制进来，而是在问答时实时查询客户的业务数据库**。所以这里的"注入"实际上是**配置连接**，而不是数据迁移：

```
用户问："上个月华南区的销售额是多少？"
  ↓
系统把这个问题翻译成 SQL
  ↓
实时查询客户的 PostgreSQL/MySQL（数据留在原地）
  ↓
把查询结果序列化后连同文档知识一起喂给 LLM 生成答案
```

需要做的只是：在配置界面填好数据库连接串，并上传一个 Schema 描述文件（YAML 格式，告诉系统每张表每个字段是什么业务含义）。

### 知识图谱数据（如果客户启用了图谱）

图谱数据有两个来源：

一是**系统入库时自动抽取**：文档入库时，系统从 Chunk 中识别命名实体（人名、产品名、组织名），并将实体和关系写入图谱。这是自动完成的，无需人工操作。

二是**手动导入已有图谱数据**：如果客户已有组织架构图、产品依赖图等结构化关系数据，可以转换为系统的实体-关系格式后批量导入。这通常需要写一次性的数据转换脚本。

## 阶段四：验收与调优

正式开放给用户之前，建议做一轮快速验收：

```bash
# 运行评测脚本
docker exec -it rag-container python scripts/evaluate.py \
  --test-set ./customer/eval_questions.yaml \
  --output ./eval_report.json
```

评测集是一个包含 20-50 个典型业务问题和参考答案的 YAML 文件，由你和客户共同准备。评测报告会给出三个关键数字：

- **召回率 Recall@20 < 0.7**：说明相关文档没被找到，需要检查同义词表或分块策略
- **忠实度 Faithfulness < 0.7**：说明 LLM 在"编"，需要检查 Prompt 或增加召回数量
- **延迟 P95 > 10s**：说明某个环节有性能问题，查 step_timings 定位

常见调优操作：

| 问题症状 | 根因 | 调优方法 |
|----------|------|----------|
| 问专有名词找不到 | 同义词缺失 | 在知识库 → 配置 → 提示词补充同义词 |
| 问题答非所问 | 分块太细，上下文断裂 | 调大 `parent_max` 参数 |
| 回答正确但来源指向错误文档 | Chunk 元数据不准 | 检查文档的章节标题识别 |
| 数值类问题答错 | 走了文档路而不是 SQL 路 | 添加该类问题的意图分类示例 |

## 完整操作时间线

```
Day 1 上午（2-4小时）
  准备基础设施（Redis/ES/Milvus，可用 docker-compose 一键启动）
  启动 RAG 服务，验证登录页可访问

Day 1 下午（2-3小时）
  UI 配置资源连接（逐一测试连通性）
  配置权限映射
  调整 System Prompt

Day 2（视文档量，1-8小时）
  批量入库客户文档
  查看入库统计，处理失败文件

Day 3 上午（2-3小时）
  运行评测脚本
  根据报告调优（同义词、分块参数）
  邀请客户代表试用，收集反馈

Day 3 下午
  修复问题，开放给更多用户
  交接运维文档（如何新增文档、如何查看日志）
```

## 一个容易误解的地方

各类数据库不是由你直接往里写数据，而是由系统的入库 Pipeline 自动写入。你只需要把原始文档（PDF、Word 等）交给系统，系统自动完成"解析 → 分块 → 向量化 → 写向量库 + 写 ES + 写图谱"的全套流程。你不需要、也不应该绕过系统直接操作向量库或 ES，否则格式会不一致，导致检索失效。

唯一的例外是业务数据库：它的数据不需要导入，系统直接实时查询，你只需要配置好连接和权限即可。
