## 1. 系统定位与目标

本系统是一套**企业级私有化 RAG 智能问答框架**，定位为可复用的交付产品。V2 在 V1 基础上重点加强了三个维度：

**文档处理工业化**：针对企业真实文档的复杂性（PDF 有文字型/扫描型/混合型/单栏双栏，Excel 有数据表和透视表，PPT 有备注）建立工业级处理流水线，每类文档有专属的处理路径和质量检测机制。

**数据一致性保障**：引入协调层（IngestionCoordinator）统管写入 MinIO、MySQL、ES、Milvus、Neo4j 五个系统的全过程，通过两阶段写入、检查点断点续写、软删除版本管理和定时一致性巡检，保障分布式写入的最终一致性。

**用户检索主权**：用户可在问答界面主动选择激活哪些检索路（向量/全文/图谱/结构化），并通过元数据筛选（文件类型/时间范围）缩小检索范围，将检索决策权从系统内部传递给用户。

│                 适配器接口层                               │
│  LLM │ Embedding │ 向量库 │ 全文检索 │ MySQL元数据        │

V2 相比 V1 的关键架构变化：在适配器层新增 **MySQL 元数据适配器**（独立于业务数据库），在框架核心层新增 **IngestionCoordinator**（入库协调层）和两个问答 Pipeline 步骤（MetadataPreFilterStep、UserRetrievalPathRouterStep）。

### 2.2 数据存储职责分工（V2 精确定义）

| 存储 | 存什么 | 服务什么场景 |
|------|--------|-------------|
| MinIO | 原始文件二进制 | 答案来源溯源，原文预览 |
| MySQL（元数据库） | 文档元数据、Chunk元数据、表格结构化数据、入库任务状态 | 元数据前置过滤、入库任务管理、一致性巡检 |
| Elasticsearch | Chunk 文本全文索引（含摘要字段高权重） | BM25 关键词检索 |
| Milvus | Chunk Embedding 向量 | 语义相似度检索 |
| Neo4j/NebulaGraph | 实体节点和关系三元组 | 多跳关系推理查询 |
| MySQL（业务库） | 客户业务数据（不迁移，实时查询） | NL2SQL 结构化查询 |
| Redis | Session 状态、三层对话记忆 | 多轮对话上下文管理 |

**元数据库的特殊定位**：MySQL 元数据库不是检索路，而是检索前的**过滤层**。它先于向量库和 ES 执行，把符合条件的 chunk_id 收窄为白名单，然后向量库和 ES 在这个白名单范围内检索，大幅提升检索精度和性能。

## 3. 核心设计原则

### 3.1 三不变三可换（继承 V1）

**不变**：Pipeline 编排逻辑、RRF 算法、Cross-Encoder 重排、三层记忆压缩、两阶段写入协议、一致性巡检规则。

**可换**：所有外部服务调用（通过适配器）、文档解析实现、业务规则注入。

### 3.2 渐进式降级（V2 强化）

资源缺失时系统自动降级而不崩溃。V2 新增降级场景：

- MySQL 元数据库不可用 → 跳过元数据前置过滤，直接进行全库检索
- 某库写入失败 → 标记 PARTIAL 状态，其他库正常可用，一致性巡检后台修复
- 所有检索路被用户关闭 → 自动回退到系统默认路（向量+BM25）

### 3.3 入库的最终一致性

写入五个存储系统的操作不可能原子化，V2 采用"顺序提交+检查点+自动恢复"三机制组合，保证最终一致：即使中间任何一步失败，系统通过检查点断点续写和定时巡检自动修复，用户不需要手动干预。

## 4. 三大主体功能域

系统的所有功能归属三个相互协作但边界清晰的域：

```
┌─────────────────────────────────────────────────────────────┐
│  功能域 A：知识库构建                                         │
│  ├── 文档入库（UI上传 / 服务器路径 / 命令行脚本）             │
│  ├── 文档类型分派（PDF文字/扫描/混合 / Word / Excel / PPT…） │
│  ├── 异步任务管理（状态机 / 进度推送 / 重试 / 幂等）          │
│  ├── 三阶段质量检测（解析 / 分块 / 入库后验证）               │
│  └── 多库一致性写入（两阶段 / 检查点 / 软删除 / 巡检）        │
└─────────────────────┬───────────────────────────────────────┘
                      │ 知识库（Milvus+ES+MySQL+Neo4j+MinIO）
┌─────────────────────▼───────────────────────────────────────┐
│  功能域 B：RAG 问答                                           │
│  ├── 查询理解（意图/改写/指代消解/话题跳转/子问题分解）        │
│  ├── 元数据前置过滤（MySQL，缩小检索范围）                    │
│  ├── 用户检索路选择（向量/BM25/图谱/结构化，用户主动控制）    │
│  ├── 多路并行召回 + RRF 融合 + Cross-Encoder 重排             │
│  ├── Session 临时文档（对话中上传，优先召回，2小时有效）       │
│  ├── 三层记忆管理（短期/工作/长期，跨轮次上下文维护）         │
│  └── Prompt 组装 + LLM 生成 + 忠实度校验 + 来源溯源          │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  功能域 C：配置管理                                           │
│  ├── 资源连接（含 MySQL 元数据库，各适配器连接配置）           │
│  ├── 功能开关（检索路 / Pipeline 步骤 / 可观测性）            │
│  ├── 知识域权限（角色 → collection 映射）                     │
│  ├── 提示词管理（System Prompt + 意图示例）                   │
│  └── 通知配置（邮件 / Webhook）                               │
└─────────────────────────────────────────────────────────────┘
```

功能域 A 和 B 之间的关联点有两处：
一是**全局知识库**（A 构建，B 查询）；
二是**Session 临时文档**（用户在 B 的对话中上传，走轻量化的 A 处理路径，只写入临时向量 collection，不入全局库）。

## 5. 知识库构建体系

### 5.1 入库方式

系统支持三种入库方式，覆盖不同规模和场景：

**UI 拖拽上传**（适合少量文档和日常维护）：在知识库管理界面拖拽文件，单次最大 500MB，支持多文件同时提交。上传后立即触发异步入库任务，用户可在任务视图中实时查看 SSE 推送的进度。

**服务器路径指定**（适合大批量首次入库）：管理员在配置界面指定允许入库的服务器根目录（`server_ingest_root`），在 UI 填写目录路径，系统直接读取服务器挂载目录的文件，无需通过 HTTP 上传，适合几十 GB 的大批量文档。

**命令行脚本**（适合 CI/CD 或定时同步）：`scripts/ingest.py` 支持目录递归扫描、并发控制、MD5 去重跳过，适合定期同步或 DevOps 场景。

### 5.2 文档类型路由

不同类型的文档在进入框架后，由文件 MIME 类型和扩展名双重判断，路由到各自的专属处理 Pipeline：

**PDF 的三条路径**：PDF 是最复杂的格式，系统在正式处理前先执行快速预检（`detect_scan_type`），读取前三页估算字符密度，判断类型：

- 文字型 PDF：走版面分析（识别单栏/双栏/多栏布局，对双栏执行列重排保证文字顺序正确）、表格提取（有边框用 pdfplumber，无边框用列对齐检测）、图片区域截取后 VLM 理解
- 扫描型 PDF：走图像预处理（去噪/倾斜矫正/二值化）→ OCR（PaddleOCR，支持中英混排）→ 置信度评估
- 混合型 PDF：逐页判断类型，文字页走文字路径，扫描页走 OCR 路径，最终合并

**Excel/CSV**：每个 Sheet 独立处理。数据表转换为"第N行：列A=值X"格式的自然语言描述入向量库/ES，同时保留原始行列结构入 MySQL table_data 表（供后续精确数值查询）。统计列的最大值/最小值/均值记录在元数据中，供元数据过滤使用。

**PPT**：每张幻灯片作为独立 Chunk，标题、正文、Speaker Notes 分别提取（备注往往包含最丰富的语义信息，重要性不亚于幻灯片正文）。

**Markdown**：识别标题层级构建大纲树，代码块作为独立 Chunk 并标注语言类型（便于后续代码类问题的精确检索）。

### 5.3 异步任务生命周期

```
PENDING（提交等待）
  ↓ 调度器取出
PARSING（文档解析中）  ← 推送进度：第N/M页
  ↓
CHUNKING（分块增强中）  ← 推送进度：已生成N个Chunk
  ↓
EMBEDDING（向量化中）
  ↓
WRITING（写入各库中）   ← 每库完成后更新 checkpoint
  ↓
DONE ─────────────────→ 触发完成通知（UI/邮件/Webhook）
PARTIAL（部分库失败）  ← 可降级使用，巡检后台修复
FAILED（已用尽重试）  ─→ 触发失败通知

任何阶段失败 → RETRYING（指数退避：1min/5min/15min，最多3次）
```

**幂等性保障**：提交时计算文件 MD5，若同内容文档已存在且状态为 DONE，直接返回已有任务，跳过处理。状态为 FAILED 的文档允许重新入库（覆盖）。

**断点续写**：每个库写入完成后在 MySQL 的 checkpoint 字段打钩（`{"minio":true,"mysql":true,"es":false,...}`）。重试时从检查点之后继续，不重复已完成的库。

### 5.4 三阶段质量检测

**解析后检测（ParseQualityCheckStep）**：

| 检测项 | 判断标准 | 处理动作 |
|--------|----------|----------|
| 文字提取率 | < 20% | 标记需要 OCR 补充 |
| OCR 置信度 | < 0.6 | 标记该页为低质量，在质量报告中记录告警 |
| 乱码率 | > 5% | 尝试重新编码，失败则记录告警 |
| 空白页比例 | > 30% | 质量报告告警 |

**分块后检测（ChunkQualityCheckStep）**：

| 检测项 | 判断标准 | 处理动作 |
|--------|----------|----------|
| 信息密度 | < 0.3 | quality_score 调低，检索时降权 |
| 过短 Chunk | token < 20 | 合并到相邻 Chunk |
| 同文档重复 | 余弦相似度 > 0.95 | 标记 duplicate，跳过入库 |

**入库后验证（PostWriteVerificationStep）**：抽样 6 个 Chunk，在 ES 和 Milvus 中各回查，验证写入正确性。验证失败触发局部补写（只补写失败的 Chunk）。

### 5.5 四库写入顺序与依赖关系

写入顺序严格按依赖关系排列，不可调换：

```
① MinIO（原文件）
       ↓ storage_url 确定后
② MySQL（documents + chunks_meta + table_data）
       ↓ chunk_id 在 MySQL 中存在后
③ ES（全文索引，按 chunk_id 检索）
④ Milvus（向量索引，按 chunk_id 检索）
       ↓ 可选
⑤ Neo4j/NebulaGraph（知识图谱）
```

每步完成后更新 MySQL checkpoint，确保故障恢复时可从断点续写。

## 6. 在线问答引擎

### 6.1 V2 完整处理流程

```
用户输入（含检索路选择和元数据过滤条件）
  ↓
① 安全过滤          → 敏感词/注入检测/权限校验
  ↓
② 查询理解          → 意图/改写/指代消解/Standalone补全/话题跳转/子问题分解
  ↓
③ 用户检索路路由    → 系统可用路 ∩ 用户选择路 → active_paths
  ↓
④ 元数据前置过滤    → MySQL 查询 chunk_id 白名单（按文件类型/时间范围）
  ↓
⑤ 多路并行召回      → 在白名单范围内：向量召回 ‖ BM25 ‖ 图谱 ‖ 结构化 ‖ 临时文档
  ↓
⑥ RRF 融合         → 多路结果合并，临时文档分数×1.2加权
  ↓
⑦ 语义去重 + Cross-Encoder 精排
  ↓
⑧ Prompt 组装       → 记忆注入 + 上下文压缩 + 引用编号绑定
  ↓
⑨ LLM 流式生成
  ↓
⑩ 忠实度校验 + 来源溯源 + 格式化输出
```

### 6.2 元数据前置过滤层

这是 V2 相比 V1 最重要的架构新增。其本质是在向量检索和 BM25 检索之前，先由 MySQL 元数据库缩小候选范围：

用户设置"只看 PDF 文档"或"只看 2024 年之后的文档"，系统先在 MySQL 中查询符合条件的 chunk_id 白名单（上限 50000 条），然后把这个白名单作为 `filter` 注入到 Milvus 和 ES 的检索请求中。检索只在这个子集范围内执行。

这带来两个收益：一是精准性提升（用户已明确排除的文档不会出现在答案中）；二是性能提升（在小子集上做向量检索比全库检索快）。

无过滤条件时，此步骤完全跳过，不产生任何额外延迟。

### 6.3 用户检索路选择

V2 将检索路的控制权从系统内部（只有意图路由决定）传递给用户：

**系统层面**（管理员在配置界面设定）：哪些检索路物理上可用（有没有接向量库？有没有接图谱？）。这是硬上限，用户无法突破。

**用户层面**（用户在问答界面设定）：在系统允许的范围内，用户可以独立开启或关闭每条检索路。选择存入 localStorage，跨 Session 记住偏好。

最终激活的检索路 = 系统启用路 ∩ 用户选择路。

### 6.4 Session 临时文档

用户在对话框上传临时文档后，系统走轻量化处理路径（跳过 VLM 图片理解、实体抽取，只做基础解析+固定窗口分块+向量化），控制在 30 秒内完成，写入 Session 专属的临时 collection（`tmp_{session_id}`）。

临时文档的 RRF 分数乘以 1.2 加权系数，在融合排序中优先于全局知识库。2 小时后 TTL 到期，Milvus 自动清理对应 collection。

## 9. 多库数据一致性体系

### 9.1 一致性挑战

一个文档入库需要写入五个系统（MinIO→MySQL→ES→Milvus→Neo4j），这五次写入不在同一事务中。常见故障场景：进程在 ES 写入后崩溃，Milvus 数据缺失；文档更新时旧版本删除后新版本写入一半失败。

### 9.2 两阶段写入协议

IngestionCoordinator 将写入过程分为两阶段：

**阶段一**（解析/分块/Embedding）：纯计算，无外部写入，失败重试成本低。

**阶段二**（顺序写入）：按依赖顺序逐库写入，每步完成后在 MySQL `WriteCheckpoint` 字段打钩。故障恢复时读取 `WriteCheckpoint`，从第一个 false 的库开始续写，已完成的库不重复写入（ES 和 Milvus 均支持 upsert 语义，重复写入安全）。

### 9.3 软删除版本管理

文档更新（覆盖入库）时不直接删除旧版本：

1. 旧版本标记为 `SUPERSEDED`（数据仍在各库中）
2. 新版本入库（checkpoint 全部完成）
3. 异步清理旧版本（从 ES/Milvus 删除旧 chunk_id，MySQL 级联删除）

这保证了在新版本写入期间，旧版本持续可用，用户不会经历"文档消失"的窗口期。

### 9.4 定时一致性巡检

每小时执行一次巡检（`ConsistencyCheckConfig` 配置）：取最近 100 个 DONE 文档，对比 MySQL 中的 chunk_id 集合与 ES、Milvus 中的实际数据，发现差集则自动补写。巡检发现的不一致数量和修复操作数量写入监控指标，差异超阈值时告警。

## V2.1 补充说明

### 业务规则注入的架构位置（§2.1 补充）

业务规则注入分散在适配器层的三个节点：`SynonymAdapter`（术语/同义词规则）、`AuthAdapter`（权限映射规则）、`SecurityFilterStep` 配置参数（合规规则）。这三个节点是框架核心调用但内容由客户注入的接口点，实现了"框架逻辑不变，业务规则可换"的设计目标。

### 默认检索路设计理由（§3.2 补充）

默认路选**向量+BM25**双路而非 BM25 单路，原因是两者的覆盖范围互补：BM25 擅长精确关键词（型号/代码/专有名词），向量检索擅长语义/意图/近义词表达，两者形成**词汇鸿沟**互补（Vocabulary Gap Complementarity）。单独使用任一路，真实业务查询中均有大量类型的召回严重不足。默认双路通过 RRF 融合取两者之长，是无需业务知识即可获得最高召回覆盖率的最优组合。

### 图片溯源（§6.1 补充）

召回内容为图片描述 Chunk 时，溯源展示优先级：`figure_label`（图28）> `figure_caption`（图题文字）> `page_num`（页码）。图片序号在版面分析阶段通过 `FigureLabelExtractor` 从图片下方紧邻文本块中正则识别，存入 `raw_data.figure_label`。

### 文档大纲与 Chunk-章节关系（§5.1 补充）

`OutlineBuilder` 在解析阶段维护标题栈，为每个 ParsedElement 生成 `section_path`（如 `"第三章 系统配置/3.1 网络参数配置/3.1.2 路由协议设置"`）。此路径存入 `chunks_meta.section_path` 字段，用于：① 元数据前置过滤（`section_path LIKE '第三章%'`）；② 溯源定位展示；③ 同章节 Chunk 聚合扩展上下文。

### 质量检测与入库阻塞（§5.4 补充）

系统**永远不因质量问题阻塞入库（不 pending 等待人工）**。低质量情况的处理策略：轻度问题（置信度 0.6-0.8）→ 告警+降权；中度问题（置信度 0.4-0.6）→ 告警+建议重传；严重问题（置信度 <0.4 或全文字符<100）→ 标记 `PARTIAL` 状态，对应 Chunk `quality_score=0.1`（检索时几乎不被召回）。管理员通过质量报告界面知晓后可选择重新上传。

### 隐式元数据意图抽取（§6.2 补充）

元数据前置过滤支持两种触发方式：① 用户在 UI 检索路面板主动设置（显式，优先）；② 系统在 `QueryUnderstandingStep` 中通过 `ImplicitMetaExtractor` 从问题语义中自动推断（隐式，在显式无值时填充）。两者通过 `merge_with_explicit()` 合并，显式设置不被隐式推断覆盖。

### 用户反馈改善机制（§6 补充）

三条闭环路径：① 即时影响：同 Session 内将负反馈注入短期记忆，LLM 感知后调整策略；② 检索权重优化：定时任务分析高频负反馈 Chunk，自动调整 `quality_score`（±0.05-0.1）；③ 意图分类优化：运营人员定期审查路由错误的反馈，补充到意图分类 few-shot 示例中。

### 本地目录批量入库（§5.1 补充）

在服务器路径入库（后端直接读取挂载目录）之外，新增**客户端本地目录**入库能力：利用 HTML5 `<input webkitdirectory>` 属性，管理员在浏览器中选择本机目录，JS 递归列出所有文件（或处理拖放的目录），以 4 并发队列逐文件上传并触发入库，实时显示上传进度。适用于管理员本机有文档、文件总量 1GB 以内的场景。
