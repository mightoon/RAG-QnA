# 一、设计文档中"文档上传与处理"的方案

## 1.1 上传（入库方式）——`architecture.md` §5.2

设计定义**四种入库方式**，全部统一创建 `IngestBatch`（单文件也建批次，`total=1`），任务视图提供批次维度聚合进度：

| 方式             | 设计要点                                                     |
| ---------------- | ------------------------------------------------------------ |
| UI 拖拽上传      | 单次最大 500MB，多文件同时提交，立即触发异步任务 + SSE 推送进度 |
| 服务器路径指定   | 管理员在配置界面指定 `server_ingest_root`，UI 填目录路径，系统直接读挂载目录，不过 HTTP，适合几十 GB |
| 本地目录批量入库 | `<input webkitdirectory>` 选本机整个目录，JS 递归列文件，**4 并发队列逐文件上传**；先预览（数量/类型分布/总大小）再确认上传；1GB 以内 |
| 命令行脚本       | `scripts/ingest.py`：目录递归、并发控制、MD5 去重跳过，用于 CI/CD 定时同步 |

## 1.2 类型路由与工作流——`architecture.md` §5.3 + `rag_framework_spec_v3.md` §7.2

- 类型由 **MIME + 扩展名双重判断**；步骤序列是**声明式 YAML 工作流注册表**（`workflows.yaml`），运行时加载、支持热重载，新增格式只加一条 workflow。
- **所有 workflow 第一步必须是 `detect_format`**（magic bytes），防扩展名伪装，检测失败直接拒绝入库。
- 条件分支用 `{condition_key: steps_list}`（spec §7.2.3 用 `StepResult.next_steps` 实现），PDF 由 `detect_scan_type` 预检前三页字符密度后动态路由 `text / scanned / mixed`。
- 各类型专属路径：PDF（版面分析→多栏重排→TOC 提取→表格/图片→VLM）、Word（Heading 层级 + 内嵌表格/图片）、Excel（每 Sheet 独立 + 结构化入 table_data + 「第N行：列A=值X」自然语言）、PPT（每页独立 Chunk，**备注并入文本流**）、图片（OCR + VLM 全图描述）、Markdown（标题树 + 代码块独立 Chunk、标语言）、HTML（去导航/广告）。
- spec §22.3 又给了 V2 的 9 条 Pipeline Key（`pdf_text/pdf_scan/pdf_mixed/word/spreadsheet/slides/plaintext/html/image`）与工厂函数 `build_ingestion_pipeline_for_task(file_type, scan_type, config, registry)`。

## 1.3 处理流水线六步——`architecture.md` §5.1（spec §7.1 给出代码级定义）

`① 解析 → ② 多模态 → ③ 智能分块 → ④ 元数据增强 → ⑤ Embedding → ⑥ 并行写入`

- **OutlineBuilder** 维护标题栈生成 `section_path`（`"第三章 系统配置/3.1 网络参数配置/..."`），PDF 用 TOC 交叉验证；三处用途：元数据前置过滤、溯源定位、同章节上下文聚合。
- **层次化分块**：父块 = 完整语义单元（≤2000 token，供 LLM），子块 = 细粒度片段（≤512 token，供检索）；边界优先级 标题 > 段落 > 句子 > 固定窗口。
- **确定性 chunk_id**：`sha256(tenant_id:doc_id:seq:content_hash[:8])[:32]` → ES/Milvus upsert 直接覆盖，免删除逻辑。
- **元数据增强**（ROI 最高）：LLM 摘要（~100 字，与正文拼接一起 Embedding）、关键词 top-10 入 ES 高权重字段、实体抽取入图谱、质量评分（低质召回时过滤）。
- **三阶段质量检测**（§5.8）：`ParseQualityCheckStep`（文字提取率 <20% 标记需 OCR 补充 / OCR 置信度 <0.6 / 乱码率 >5% / 空白页 >30%）、`ChunkQualityCheckStep`（信息密度 <0.3 降权 / token<20 合并 / 重复余弦 >0.95 跳过）、`PostWriteVerificationStep`（抽 6 块在 ES+Milvus 回查，失败触发**局部补写**）。
- **不阻塞入库**：轻度→告警降权，中度→建议重传，严重（置信度<0.4 或全文<100 字）→ `PARTIAL` + `quality_score=0.1`。

## 1.4 任务模型与写入一致性——§5.6 / §5.7 / §9

- 状态机 `PENDING→PARSING→CHUNKING→EMBEDDING→WRITING→DONE/PARTIAL/FAILED`，任何阶段失败 → `RETRYING`（指数退避 1min/5min/15min，最多 3 次）。
- 两级任务：`IngestBatch`（total/succeeded/failed/pending + 状态）→ `IngestTask × N`。
- **幂等**：提交算文件 MD5，同内容且 `DONE` 直接返回已有任务；`FAILED` 允许重入覆盖。
- **断点续写**：每库写完在 checkpoint 打钩 `{"minio":true,"mysql":true,"es":false,...}`，重试从断点之后继续。
- **写入顺序严格不可调换**（§5.8）：`MinIO → MySQL(documents+chunks_meta+table_data) → ES → Milvus → Neo4j(可选)`，依赖关系是 `storage_url` 先进、`chunk_id` 先进 MySQL。
- 另配套：软删除版本管理（`SUPERSEDED`）、定时一致性巡检、完成通知（UI/邮件/Webhook）、Session 临时文档（轻量 30s、`tmp_{session_id}`、TTL 2h、RRF ×1.2）。
- spec §22.9 端点表（`/api/v1/ingest/upload`、`/server-path`、`/tasks`、`/tasks/{id}/progress`、`/tasks/{id}/retry`、`/quality/{doc_id}`、`/ephemeral`）。

### C. 同名不同实现 / 设计被替换

1. **状态机状态集不一致。** 设计 `PENDING/PARSING/CHUNKING/EMBEDDING/WRITING/DONE/PARTIAL/FAILED/RETRYING/SUPERSEDED`；代码一致（`models.py:46-57`）并**多出 `DELETED`（回收站）**。但前端/UI 层还在用另一套词：`queued/uploading/indexing`（`knowledge-tasks.js:4`、`routes.py:2877`、`_macros.jinja2:2-7`），这些值**永远不会出现**，而真实活动态 `pending/chunking/writing` 不在活动集里 → 活动任务徽标与"进行中"过滤长期为空。
2. **缺少任务进度。** 设计 `IngestTask.progress` 是带阶段权重的属性（spec 附录 C P-01）；代码 `models.py:184-207` **没有 `progress` 字段**，`routes.py:2918` 取到 `None`。前端队列视图 `_queue_view`（`routes.py:3101-3110`）依赖 `queue.maxsize`，而协调器用的是无界队列（`coordinator.py:46`）→ 队列上限/队列满提示永远是空。
3. **`PARTIAL` 语义被放宽。** 设计：只有"部分库写入失败"才是 PARTIAL（§5.6）；代码 `FinalizeStep`（`ingest_write.py:308-309`）把**任何 warning**（如"标题与书签匹配率低""双栏重排"）都判成 `PARTIAL`，并顺带把批次算成 `partial_failed` 触发通知 —— 会出现"全库写入成功却报部分完成"。
4. **冲突解决机制换实现。** 设计用「同文档 chunk 余弦 >0.95 标 duplicate 跳过」；代码用归一化文本指纹（`ingest_chunk.py:110-114`）。
5. **Embedding 输入。** 设计要求"摘要+关键词+正文"一起向量化（§5.5、spec Step 5 `_build_embed_text`）；代码 `EmbedStep` 只对 `chunk_texts`（正文）做 `embedding.embed`，摘要/关键词只进 ES。这会让向量丢掉摘要带来的信息密度增益。
6. **配置项名/单位漂移。** 设计 `consistency.interval_minutes / sample_size / auto_repair`、`ephemeral.priority_boost`；代码是 `interval_hours / sample_docs / alert_threshold`（`config/models.py:603-607`）与 `retrieval.ephemeral_score_boost`（`config/models.py:540`），且巡检修复**总是尝试**、没有 `auto_repair` 开关。
7. **目录/文件结构漂移。** 设计 `rag/core/ingestion_coordinator.py`、`rag/core/ephemeral_knowledge.py`、`rag/core/notification_service.py`、`rag/pipeline/ingestion/{steps,pipeline,quality_steps}.py`、`rag/adapters/builtin/mysql_meta/…`；代码落在 `rag/ingestion/coordinator.py`、`rag/services/{ephemeral,notifications,consistency}.py`、`rag/pipeline/steps/ingest_*.py`、`rag/adapters/{meta_mysql,doc_parser}.py`（平铺）。功能对得上，路径与文档不符。
8. **本地路径入库适配器被整体替换。** 设计有 `rag/adapters/builtin/synonym/file_based.py` 等 builtin 目录分层；代码是单文件适配器 + `AdapterRegistry`。
9. **巡检的父块口径有真实缺陷。** `consistency._check_doc`（`consistency.py:99-107`）用 MySQL 全量 chunk（含父块）比 Milvus 集合（父块不入向量库），只容忍 10% 缺失。而父块数≈子块数，缺失比例天然 ~50%，**每个文档都会被判不一致**并触发一次无效补写（补写时又 `child = [...] if not c.is_parent` 排除父块，实际修不动）。设计里的"抽样巡检"因此退化为常态化误报。

### D. 代码超出设计（架构文档已补记）

- **向量空间指纹门禁**（TS-022）：写入前判 `vector_write_blocked`，指纹不一致就"有意跳过"而非报错写成 PARTIAL，并在 `enabled_paths` 里摘掉向量路（`container.py:998-1070`、`ingest_write.py:130-144`、`consistency.py:139-158`）。`architecture.md:633` 有对应说明。
- 反馈闭环微调 chunk 质量分（`meta_mysql.adjust_chunk_quality`）、`entities` 表与 `EntityLinker` 归一化、图题溯源 `figure_label/figure_caption`（`ingest_chunk.py:28-60`）等，是设计未细列的实现增量。

# 三、结论摘要（按严重度）
