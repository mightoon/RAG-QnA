## 1. 系统定位与目标

本系统是一套**企业级私有化 RAG（检索增强生成）智能问答框架**，定位为可复用的交付产品，而非一次性定制开发。其核心价值在于：

**面向客户**：将客户的私有知识（文档、数据库、业务系统）转化为可对话的智能问答能力，员工无需学习复杂的搜索技巧，直接用自然语言提问即可获得基于权威来源的准确答案，并可追溯原始文档。

**面向交付**：同一套框架代码部署到不同客户环境，只需配置文件和少量适配代码即可运行，不依赖任何特定的大模型服务商、向量数据库或认证系统，最大限度降低现场交付成本。

系统具备以下核心能力：

- 多格式文档的自动化解析、分块与向量化入库
- 四路异构知识库的协同检索与融合排序
- 多轮对话上下文记忆与跨会话知识积累
- 答案的来源溯源与忠实度自动校验
- 完整的知识库管理与系统配置 Web 界面
- 基于角色的多租户数据隔离与权限控制

## 2. 整体架构概览

系统在垂直方向分为五个层次，自上而下分别是：用户接入层、框架编排核心层、适配器接口层、外部资源层，以及贯穿全局的运维控制面。

### 2.2 两条核心数据流

系统的所有业务逻辑归结为两条相互独立的数据流：

**离线入库流****（Ingestion Pipeline）**：由管理员触发，将原始文档转化为可检索的知识表示，写入多个存储系统，是系统知识能力的来源。

**在线问答流**（Query Pipeline）：由用户触发，将自然语言问题转化为精准答案，是用户直接感知的价值。

两条流程共享底层的适配器层和外部资源层，但在编排逻辑、执行时机和性能要求上完全独立。

## 3. 核心设计原则

### 3.1 三不变三可换

框架的可维护性建立在一条明确的边界上：**算法逻辑不变，外部依赖可换**。

**不变的部分**构成框架的核心价值和技术护城河：Pipeline 编排逻辑、RRF 融合算法、Cross-Encoder 重排策略、三层记忆压缩机制、token 预算分配规则、可观测性埋点位置。这些内容在所有客户部署中完全一致，是系统质量的保证，不因现场情况而改变。

**可换的部分**构成系统的灵活性：所有外部服务调用（LLM、向量库、全文检索、存储）、各客户不同的数据格式转换逻辑、业务规则（同义词、权限映射、敏感词过滤）。通过适配器模式，这些部分可以在不触碰框架核心的前提下独立替换。

### 3.2 渐进式降级

当某类外部资源不可用时，系统不崩溃，而是自动降级到更简单但仍可用的工作模式：

- 知识图谱不可用 → 跳过图谱召回路，用向量 + 关键词双路召回
- 业务数据库未连接 → 跳过结构化查询路，不影响文档问答
- Cross-Encoder 重排模型未加载 → 退回 RRF 融合得分排序
- 召回结果为空 → 明确提示知识库无相关内容，而非幻觉生成

这种设计使系统在部分资源缺失时仍能以降级模式向用户提供服务。

### 3.3 配置即产品

从框架到可运行的客户专属系统，核心媒介是一个 YAML 配置文件（`customer_config.yaml`）。该文件描述了客户环境中所有资源的位置、凭证、参数，以及功能开关和行为参数。配置文件的变更可在不重新部署代码的情况下改变系统行为，是交付物中最重要的客户化产物。

## 4. 知识库构建体系

### 4.1 整体流程

入库流程是一条单向的数据处理管道，将原始文件转化为分布在四个存储系统中的结构化知识表示。整个流程由六个步骤顺序执行，每步处理上一步的输出。

```
原始文件
  ↓
① 文档解析      → 识别文字/表格/图片/代码，分离噪声内容
  ↓
② 多模态处理    → 图片/图表调用 VLM 生成文字描述
  ↓
③ 智能分块      → 按语义边界切分，构建父子层次 Chunk 结构
  ↓
④ 元数据增强    → 生成摘要、抽取关键词和实体、计算质量分
  ↓
⑤ Embedding     → 将摘要+关键词+正文拼接后向量化
  ↓
⑥ 并行写入      → 同时写入向量库、全文索引、知识图谱、原文存储
```

### 4.2 文档解析子系统

文档解析是整个知识质量的第一道关卡，也是质量最容易损失的环节。系统针对不同文件类型使用专门的解析策略：

**PDF 文档**：使用版面分析工具识别页面元素的位置和类型，区分正文段落、标题层级、表格区域、图片区域、页眉页脚（过滤），避免混排内容的错误拼接。

**Word 文档**：利用文档结构模型直接提取各级标题（Heading 1/2/3）、正文段落、内嵌表格、内嵌图片，保留完整的层级结构信息作为后续分块和路径生成的依据。

**图片与扫描件**：通过 OCR 提取文字，对包含流程图、时序图、架构图等非文字内容的图片，调用多模态大模型（VLM）生成描述性文字，使图片内容进入语义检索体系。

**表格内容**：表格的处理采用双轨策略——将表格转换为"第N行：列A=值X，列B=值Y"格式的自然语言描述，供语义检索使用；同时保留原始行列结构存入关系数据库，供精确的结构化查询使用。

### 4.3 智能分块策略

分块是 RAG 系统中对检索效果影响最大的工程决策。系统采用**层次化分块**而非简单的固定窗口切分：

**父节点**代表完整的语义单元（整个段落或小节，约 2000 token 上限），包含足够的上下文，适合提供给 LLM 生成完整连贯的答案。

**子节点**代表细粒度的语义片段（单个句子或短语，约 512 token 上限），粒度足够小，适合精确定位和相关性计算。

检索时使用子节点定位最相关的细粒度内容，但喂给 LLM 时取回对应的父节点完整内容，兼顾检索精度和生成质量。

分块边界的选取遵循优先级：标题边界 > 段落边界 > 句子边界 > 固定 token 数截断。

### 4.4 元数据增强

元数据增强是入库阶段 ROI 最高的工程投入。每个子 Chunk 在写入存储前，系统会并发执行以下增强操作：

- **摘要生成**：调用轻量 LLM 生成 1-2 句核心内容摘要（约 100 字），摘要与正文拼接后一起 Embedding，使向量同时捕获关键信息和细节内容；摘要在后续检索时也用于上下文压缩
- **关键词抽取**：提取 top-10 专业关键词，写入全文索引的专用字段（检索权重高于正文）
- **实体识别**：抽取人名、产品名、组织名等命名实体，用于知识图谱写入和图谱召回路的实体锚定
- **质量评分**：评估 Chunk 的信息密度（中文内容占比、噪声符号占比等），低质量 Chunk 在召回时会被过滤

### 4.5 四库并行写入

入库的最终步骤是并发写入四个存储系统，各存储的职责明确分工：

| 存储系统 | 写入内容 | 服务的检索场景 |
|----------|----------|----------------|
| 向量库（Milvus/Qdrant） | 子节点 + 父节点的 Embedding 向量及元数据 | 语义相似度检索，处理意图驱动的模糊查询 |
| 全文索引（Elasticsearch） | 所有 Chunk 的文本内容、摘要、关键词、元数据 | BM25 关键词检索，处理精确术语、型号、代码等 |
| 知识图谱（Neo4j/NebulaGraph） | 从实体列表构建的节点和关系三元组 | 多跳关系推理，处理"A 的 B 的 C 是什么"类型的关系查询 |
| 对象存储（MinIO） | 原始文件二进制 | 答案来源溯源时提供原文预览链接 |

关系数据库还存储文档级元数据（文件名、大小、入库状态、所属 collection）和结构化业务数据，供 NL2SQL 查询路使用。

## 5. 在线问答引擎

### 5.1 整体流程

在线问答流程是一条实时处理管道，从用户输入到流式答案输出，经过八个顺序步骤，每步均可通过配置独立启用或禁用。

```
用户输入
  ↓
① 安全过滤      → 敏感词检测、注入攻击识别、权限校验
  ↓
② 查询理解      → 意图分类、指代消解、Standalone 补全
  ↓
③ 查询改写      → 同义词扩展、多路改写、子问题分解
  ↓
④ 意图路由      → 决定激活哪几路召回
  ↓
⑤ 多路并行召回  → 向量召回 ‖ BM25 ‖ 图谱 ‖ 结构化查询（并发执行）
  ↓
⑥ 融合与重排    → RRF 融合 → 语义去重 → Cross-Encoder 精排 → 截断
  ↓
⑦ Prompt 组装   → 上下文压缩 → 记忆注入 → 引用编号绑定
  ↓
⑧ 生成与后处理  → LLM 流式生成 → 忠实度校验 → 来源溯源 → 格式化输出
```

### 5.2 查询理解子系统

查询理解是整个在线流程中对召回质量影响最大的单一环节。用户的自然语言提问和知识库文档的书面表达之间存在固有的词汇鸿沟，查询理解的核心任务是弥合这个鸿沟。

**意图分类**将问题划分为六类：事实查询（Factual）、关系推理（Relational）、聚合统计（Aggregation）、步骤流程（Procedural）、对比分析（Comparative）、闲聊（Chitchat）。意图类型直接决定后续路由到哪些召回路——闲聊直接由 LLM 生成，无需检索；聚合统计路由到 NL2SQL；关系推理激活图谱路。

**指代消解**处理多轮对话中的代词和省略：将"它支持多少端口？"还原为"X300 交换机支持多少端口？"，将"那第二条呢？"还原为完整的独立问题。这一步骤是多轮对话场景下召回准确性的关键前提。

**Standalone 补全**将当前轮的问题（可能是追问、省略主语的问题）改写为一个完整的、无需上下文即可理解的独立查询，用于后续的向量化和检索。

**话题跳转检测**通过计算当前问题向量与工作记忆中话题向量的余弦相似度，判断用户是否切换了话题。检测到跳转时重置话题相关的实体槽位，避免旧话题的上下文污染新话题的检索。

**复合问题分解**将"比较 A 和 B 的价格、性能和售后"这类复合问题分解为多个原子子问题，分别检索后在生成阶段合并，解决单一检索无法覆盖多维度问题的问题。

### 5.3 多路并行召回

四路召回基于各自不同的检索原理，互补覆盖不同类型的信息需求，且并发执行以控制延迟。

**向量语义召回**：将 Standalone 查询及其多路改写版本分别向量化，在向量库中执行 ANN（近似最近邻）检索，每路取 top-20 结果后合并去重。这一路的优势是语义理解能力——即使用词不同，只要含义相近就能命中；劣势是对精确术语（型号、代码）的召回不稳定。

**BM25 关键词召回**：对改写后的查询在 Elasticsearch 中执行全文检索，同时匹配正文字段（权重 1.0）和摘要字段（权重 1.5）。BM25 在精确术语匹配上天然更稳健，与向量召回形成互补。

**知识图谱召回**：从问题中提取命名实体，在图谱中定位对应节点，然后做 1-3 跳的关系遍历，返回实体间的关系链路并序列化为自然语言。这一路专门处理多跳关系问题，是向量和 BM25 无法处理的盲区。

**结构化数据召回**：将自然语言问题转换为 SQL（NL2SQL），查询客户的业务数据库，返回精确的数值、统计或记录。用于处理"上个季度的销售额是多少"这类需要实时数据的聚合统计类查询。

每路召回都有独立的超时控制（默认 5 秒），某路超时只记录警告，不阻塞其他路的结果返回。

### 5.4 融合与重排子系统

多路召回的结果处于不同的量纲体系（向量余弦相似度 0-1；BM25 分数无上界），需要统一融合和精排后才能作为 Prompt 上下文。

**RRF 融合（倒数排名融合）**：不依赖各路的原始分数，只依赖排名，为每个文档计算 `Σ 1/(rank_i + 60)` 的融合分数，天然解决量纲不一致问题。这一步将所有路的结果合并为一个统一排名列表（约 40 个候选）。

**语义去重**：融合列表中可能存在内容高度重叠的 Chunk（同一原文的不同版本，或父子节点）。通过计算两两余弦相似度，语义相似度超过阈值（0.92）的 Chunk 只保留得分更高的一个，避免上下文中充斥重复信息。

**Cross-Encoder 精排**：对去重后的 top-40 候选，使用 Cross-Encoder 模型（如 BGE-Reranker）对每个（查询, 候选文本）对联合建模打分（0-1）。Cross-Encoder 的精度显著高于向量相似度（因为它是联合建模而非独立向量的点积），低于阈值（0.3）的候选被过滤，最终保留 top-6 进入 Prompt。

### 5.5 Prompt 构造与生成

**Prompt 组装**将记忆层信息、检索结果、用户问题按固定结构拼接，总 token 预算约 7000：

- System Prompt（角色定义、引用格式要求）：约 300 token，固定
- 用户画像（专业背景、偏好格式）：约 200 token，从长期记忆加载
- 工作记忆（对话摘要、已确认实体）：约 400 token，每轮更新
- 短期记忆（最近 3-5 轮完整 Q&A）：约 1500 token，动态裁剪
- 检索上下文（top-6 Chunk，各带编号标签）：约 4000 token，本轮检索
- 当前问题（Standalone 补全版本）：约 200 token

排列顺序遵循"最相关内容放首位"原则，规避 LLM 对中间内容注意力衰减的问题（Lost in the Middle 效应）。

**来源溯源**通过引用编号绑定实现：每个 Chunk 在 Prompt 中标注 `[文档1]`、`[文档2]` 等编号，并要求 LLM 在关键陈述后引用来源编号，生成后系统解析引用关系，将编号映射回实际文档和页码，供用户点击查看原文。

**忠实度校验**在生成完成后，用 LLM 对答案和召回文档做一轮独立评判，输出 0-1 的忠实度分数。低于阈值（0.6）时在答案末尾追加免责声明，明确提示用户该答案的部分内容超出知识库范围。

## 6. 多轮对话记忆体系

### 6.1 三层记忆架构

多轮对话的核心矛盾是：LLM 的上下文窗口有限，但用户的对话历史无限增长。系统用三个粒度不同的记忆层次解决这个矛盾，各层在信息密度和持久性上形成梯度。

```
短期记忆（In-Context）
  最近 3-10 轮的完整 Q&A，直接放入 Prompt
  存储：动态维护在 Session 状态中（Redis）
  特点：完整准确，但容量受 token 预算限制
         ↓ 超出上限时压缩
工作记忆（Session Summary）
  对话摘要 + 实体槽位 + 话题链路
  存储：Redis，与 Session 状态同存
  特点：压缩态，信息密度高，捕获关键约束和已确认事实
         ↓ Session 结束时归档
长期记忆（Cross-Session）
  用户画像 + 历史 Session 摘要向量 + 纠错记录
  存储：关系数据库（用户画像）+ 向量库（摘要检索）
  特点：跨会话持久化，在新 Session 开始时加载
```

### 6.2 记忆的流转机制

**短期记忆的滚动压缩**：当短期记忆超过 token 阈值（约 1500 token）时，系统将最早的若干轮从短期记忆中弹出，通过异步 LLM 调用将被弹出内容合并到工作记忆的滚动摘要中，同时从 Prompt 中移除那些轮次的原文。这一过程在答案返回后的后台异步执行，不影响主链路延迟。

**实体槽位的持续更新**：系统维护一个结构化的实体状态字典，记录对话中出现并被确认的关键实体（当前产品型号、用户角色、约束条件、待确认事项），每轮对话后异步更新。槽位信息直接用于 Standalone 补全（补入省略的主语）和路由决策（已知产品型号时直接精确匹配）。

**话题链路追踪**：工作记忆中维护话题跳转路径（如"产品选型 → 技术规格 → 网络配置 → 故障排查"），用于判断当前意图的话题域归属，并作为检索过滤条件缩小召回范围。

**Session 归档**：用户结束对话或超过无活动时限后，系统触发归档流程：生成本 Session 的完整摘要，向量化后写入用户专属的长期记忆向量空间，同时更新用户画像（专业背景、偏好格式、常用产品、纠错记录）。下次对话开始时，用新问题在历史 Session 中检索最相关的历史上下文注入 Prompt。

### 6.3 话题跳转的处理

当检测到用户切换话题时，系统执行选择性记忆重置：清除话题相关的实体槽位（当前话题、待确认事项）和话题向量，但保留用户身份信息和跨话题稳定的约束（如用户角色、设备型号）。这避免了旧话题的上下文污染新话题的检索，同时保留了对用户身份的持续理解。

## 7. 适配器层与外部资源集成

### 7.1 适配器模式的本质

适配器层是系统框架化交付的技术基础。它在框架编排核心和外部资源之间建立了一层标准化接口，使核心逻辑对具体的外部服务实现无感知。

每类外部资源对应一个抽象基类（接口契约），定义该类资源的标准操作集合。框架核心只调用抽象基类的方法，不依赖任何具体实现。不同客户环境中的具体服务（不同厂商的 LLM、不同品牌的向量库）通过继承基类并实现其方法来接入框架，对框架核心完全透明。

### 7.2 十类适配器

系统定义十类适配器，覆盖所有外部依赖：

**LLM 适配器**负责与大语言模型推理服务的交互，提供文本生成（流式和非流式）、token 计数、以及系统自用的高层能力（查询改写、意图分类、摘要压缩、忠实度评估）。框架默认实现兼容 OpenAI Chat Completions API 格式，可通过配置对接任何提供该格式接口的服务，包括国产模型的 OpenAI 兼容端点和本地部署的 vLLM 服务。

**Embedding 适配器**将文本转化为固定维度的向量表示，支持批量处理，并为 BGE 系列模型提供查询前缀注入（显著提升检索效果）。入库和检索必须使用完全相同的适配器实例，以确保向量空间的一致性。

**向量库适配器**封装向量数据库的写入、检索、删除操作，支持基于元数据的过滤条件（权限、时间范围、所属 collection），并能按 doc_id 批量删除（知识更新时使用）。内置 Milvus、Qdrant、pgvector 三种实现。

**全文检索适配器**封装 BM25 全文检索操作，定义包含内容字段、摘要字段（高权重）、关键词字段的索引结构，支持中文 IK 分词器配置。内置 Elasticsearch 和 OpenSearch 两种实现。

**文档解析适配器**按文件类型路由到对应的解析实现，输出统一格式的结构化文档对象（元素列表，含类型、文本、坐标等）。内置 PDF、DOCX、图片（OCR）三种解析器。

**业务数据适配器**提供自然语言到 SQL 的转换、SQL 安全校验、查询执行和结果脱敏能力，Schema 描述通过 YAML 文件配置，支持 any SQLAlchemy 兼容的关系数据库。

**知识图谱适配器**提供实体查找、多跳关系遍历、实体和关系的写入能力，以及将图查询结果序列化为自然语言的 to_text 方法。内置 Neo4j 和 NebulaGraph 两种实现，两者在查询语言（Cypher vs nGQL）和连接协议（Bolt vs Thrift）上存在差异，均通过各自的适配器封装，对框架核心完全透明。

**同义词适配器**提供术语扩展（一个词映射到所有同义词）和术语归一化（将口语替换为知识库中的标准术语）。支持从 Excel 或 YAML 文件热加载，也可对接客户的专有术语 API 服务。

**认证权限适配器**验证用户身份 Token，返回包含用户 ID、角色列表、租户 ID 的用户上下文，供后续的权限过滤使用。内置 JWT 和 OIDC（标准协议）两种实现。

**对象存储适配器**管理原始文件和多媒体内容的存储，提供上传、下载、删除和生成临时预览 URL 的能力。内置 MinIO（S3 兼容）和本地文件系统两种实现。

### 7.3 适配器注册机制

框架提供一个中央注册中心（AdapterRegistry），在系统启动时将所有适配器类（含内置和客户自定义）按名称注册。配置文件中通过 `adapter: "名称"` 字段指定使用哪个实现，注册中心在运行时动态实例化对应的类并注入配置。这一机制使得在不修改任何框架代码的前提下，通过修改配置文件即可切换底层服务。

### 7.4 客户资源对接分类

客户现场的对接工作按复杂度分为三类：

**纯配置**（0 行代码）：客户使用的服务恰好在框架内置列表中（如 Milvus、Elasticsearch、OpenAI 兼容接口、OIDC 认证），只需在 YAML 文件中填写连接信息和凭证。

**适配器实现**（50-200 行代码）：客户使用的服务框架未内置（如私有 RPC 格式的 LLM 接口、非标准认证系统、工业图纸解析），需继承对应抽象基类实现若干方法，工作量通常在 1-4 天以内。

**资源禁用**（1 行配置）：客户没有某类资源（如无知识图谱），在配置中设置 `enabled: false`，对应的召回路自动跳过，系统降级运行。

## 8. 用户界面体系

### 8.1 技术定位

前端界面采用无构建步骤的技术方案：原生 HTML + CSS + Vanilla JavaScript，以 Alpine.js 处理响应式交互逻辑，由 FastAPI 后端直接托管静态文件和 Jinja2 服务端渲染模板。这一选择的核心理由是现场部署简单——无需 Node.js、无需 npm 构建，复制文件即可运行，与框架整体"降低交付成本"的目标一致。

### 8.2 三个核心界面

**聊天对话界面**是用户的主要使用入口，采用三栏布局：左侧侧边栏展示历史会话列表，中间主区为对话消息流，右侧可展开引用来源抽屉。

核心交互细节：消息区域支持 Markdown 渲染和代码块语法高亮；AI 回答中的引用编号（如 `[文档1]`）可点击，展开显示原始文档标题、章节、页码和预览链接；输入框支持 `Enter` 发送和 `Shift+Enter` 换行；AI 生成过程中实时流式展示 token，支持用户随时点击停止；新建会话、历史会话切换、会话重命名和删除均在侧边栏完成；多个知识域（collection）时显示知识域选择器，用户可选择在特定知识范围内提问。

**知识库管理界面**面向管理员，提供文档的完整生命周期管理：支持拖拽上传（PDF/Word/TXT/图片），上传后自动触发入库 Pipeline，通过进度条实时显示入库任务状态（等待、处理中、成功、失败）；文档列表展示文件名、文件类型、Chunk 数量、大小和入库时间，支持按 collection 切换视图；支持单文档删除（同步清除向量库、ES 和图谱中的所有相关 Chunk）、批量删除和重新索引（覆盖已有 Chunk）；顶部统计卡实时展示当前 collection 的文档总数和 Chunk 总数。

**系统配置界面**面向系统管理员，通过四个 Tab 组织所有配置项：

- **资源连接 Tab**：展示所有外部资源（LLM、向量库、ES、图谱、对象存储、Redis、业务数据库）的连接配置表单，每个资源块末尾提供"测试连接"按钮，实时显示连接状态（正常/失败/未启用）
- **功能开关 Tab**：以 Toggle 控件展示各召回路（向量、BM25、图谱、结构化）和 Pipeline 步骤（图片理解、重排、忠实度校验）的启用状态，提供召回参数（top_k、重排阈值）的数值调整
- **知识域权限 Tab**：表格形式展示角色到 collection 的映射，支持新增、编辑和删除权限条目
- **提示词 Tab**：System Prompt 的富文本编辑，以及意图分类 few-shot 示例的增删改

配置界面内置变更追踪：有未保存更改时顶栏显示提示，提供"撤销更改"按钮恢复到上次保存状态；保存时敏感字段（API Key、密码）若用户未修改则保留原值，不因界面操作被清空。

### 8.3 前后端交互模式

界面与后端的交互采用两种模式：

**SSE 流式问答**：用户发送问题后，浏览器向后端建立 Server-Sent Events 连接。后端依次推送三类事件：检索完成后立即推送来源列表（用户看到引用来源），然后逐 token 推送生成内容，最后推送完成信号（含 session_id 和 AI 自动生成的对话标题）。这一设计使用户在等待生成时即可看到答案的依据来源，提升可信度感知。

**REST API**：其余操作（会话管理、文档管理、配置读写、连接测试）均通过标准 RESTful JSON 接口交互，接口由框架的 FastAPI 路由层提供。

## 9. 安全与权限体系

### 9.1 多层安全防护

系统在多个层次实施安全控制，从外到内依次为：

**输入安全**（SecurityFilterStep）：问答 Pipeline 的第一步，强制执行敏感词过滤、Prompt 注入检测（识别"忽略之前的指令"等注入模式）、查询长度限制，任一检测命中则立即终止后续步骤，直接返回安全提示。

**认证安全**（AuthMiddleware）：所有 API 请求在到达业务逻辑之前通过认证中间件，验证 Bearer Token 并提取用户上下文（user_id、roles、tenant_id）。Token 验证委托给 AuthAdapter，支持 JWT 自签和 OIDC 单点登录两种模式。

**权限过滤**（数据库查询层）：用户的角色列表通过配置文件映射为可访问的 collection 白名单，这个白名单在每次检索时作为硬性过滤条件注入向量库和 ES 的查询中，在数据库层面执行过滤，而非在应用层过滤，从根本上防止越权数据泄露。

**数据隔离**（tenant_id）：向量库和全文索引的所有读写操作必须携带 tenant_id，租户之间的数据在同一物理集群中逻辑隔离，互不可见。

**SQL 安全**（BusinessDataAdapter）：NL2SQL 生成的语句在执行前必须通过白名单校验（只允许 SELECT，只允许访问配置中声明的表），并对结果中的敏感字段（手机号、身份证号等）自动脱敏。

### 9.2 知识域权限模型

系统采用基于角色的知识域访问控制（RBAC on Collections）：

- 知识库按业务属性划分为若干 collection（如技术文档、HR 文档、销售案例）
- 每个角色被授权访问特定的 collection 集合（`*` 代表全部）
- 权限映射在配置文件中声明，可通过配置界面动态编辑
- 文档入库时可指定 `allowed_roles` 限制访问范围
- 检索时以用户角色和知识域白名单的交集作为过滤条件

这一模型支持灵活的权限场景：运维工程师只能看到技术文档，HR 只能看到 HR 文档，管理员可看到全部。

## 10. 可观测性与运维体系

### 10.1 可观测性三支柱

系统的可观测性覆盖日志、指标和追踪三个维度，通过标准化接口对接客户现有的监控平台：

**结构化日志**：使用 structlog 输出 JSON 格式日志，每条日志携带 session_id、tenant_id、step_name 等上下文字段，便于在日志平台（ELK、Splunk 等）中按维度过滤和分析。

**Prometheus 指标**：定义一套标准指标集，涵盖查询总次数（按意图类型和状态分）、各 Pipeline 步骤延迟分布、召回分数分布、知识库 Chunk 总数、活跃 Session 数。指标推送到 Prometheus Push Gateway，通过 Grafana 可视化。

**OpenTelemetry 链路追踪**：每次请求生成一个 Trace，每个 Pipeline 步骤作为一个 Span，包含步骤名称、耗时、召回数量、错误信息等属性。支持导出到 Jaeger 或其他 OTLP 兼容的追踪后端，用于定位延迟瓶颈和排查错误。

### 10.2 知识库质量运维

系统提供批量入库脚本和评测脚本两个运维工具：

**批量入库脚本**（`scripts/ingest.py`）支持单文件和目录批量入库，并发控制（默认 4 并发），按文件 MD5 去重（内容未变则跳过），实时显示入库进度和 Chunk 数量，入库完成后汇总统计成功/失败数量。

**评测脚本**（`scripts/evaluate.py`）基于预定义的测试问题集（YAML 格式，包含问题和参考答案），批量运行完整问答流程，计算三项核心质量指标：忠实度均值（Faithfulness，衡量答案是否基于召回内容）、召回率（Recall@20，衡量相关文档是否被召回）、平均延迟和 P95 延迟。评测结果输出为 JSON 报告，是调优分块策略、同义词表和召回参数的数据依据。

### 10.3 运维管理 API

系统提供以下运维 API 供管理界面调用：

- **全组件健康检查**：逐一调用所有适配器的 health_check()，返回各组件状态和延迟
- **知识库统计**：查询各 collection 的文档数和 Chunk 数
- **文档删除**：从向量库、ES 和图谱级联删除指定文档的所有数据
- **同义词热重载**：无需重启服务，即时更新同义词表
- **入库任务状态查询**：通过 task_id 轮询异步入库任务的处理进度
- **连接测试**：对指定组件的配置做实时连接验证

## 11. 部署架构与交付模式

### 11.1 单体化部署

系统采用单体 Docker 镜像部署，包含：

- FastAPI 应用（含 API 路由、页面路由、静态文件托管）
- 前端静态资源（CSS/JS）和 Jinja2 模板
- 框架核心包（`rag/` 目录）
- 客户适配器和配置文件（`customer/` 目录）
- 预下载的 Cross-Encoder 重排模型

这种打包方式使得整个系统对客户呈现为单一服务，降低运维复杂度。

### 11.2 外部依赖的部署边界

系统本体是无状态的（Session 状态外置到 Redis），所有存储依赖均为外部服务：

```
系统服务（Docker）
  ├── FastAPI 应用（无状态）
  │
外部依赖（客户自有或新建）
  ├── Redis             ← Session 状态缓存
  ├── Milvus/Qdrant     ← 向量存储
  ├── Elasticsearch     ← 全文索引
  ├── MinIO/对象存储     ← 原文件存储
  ├── Neo4j/NebulaGraph ← 知识图谱（可选）
  ├── PostgreSQL        ← 业务数据库（可选）
  └── LLM/Embedding     ← 模型推理服务（客户私有部署或 API）
```

这一边界设计使框架容器本身可以水平扩展（多实例），所有状态都在外部存储中。

### 11.3 现场交付流程

完整的现场交付分为七个阶段：

1. **资源盘点**：梳理客户现有的存储、模型、认证基础设施，对照内置适配器清单确认对接方式
2. **配置文件编写**：填写 `customer_config.yaml`，配置各资源的连接信息和功能开关
3. **适配器开发**（视情况）：若客户使用框架未内置的服务，继承对应抽象基类实现适配器
4. **知识入库**：执行批量入库脚本，将客户文档写入知识库，确认 Chunk 数量和质量
5. **评测调优**：运行评测脚本，根据召回率和忠实度指标调整分块参数、同义词表和召回阈值
6. **上线部署**：构建 Docker 镜像，部署到客户的 Kubernetes 或虚拟机环境
7. **持续运维**：监控质量指标，迭代优化同义词表，处理新文档的增量入库

## 12. 性能特征与质量基准

### 12.1 延迟分解

从用户发送问题到开始接收流式回答，各阶段的时间消耗如下（P50 目标）：

| 阶段 | 耗时目标 | 主要优化手段 |
|------|----------|-------------|
| 安全过滤 + 查询理解 | ~300ms | 小模型（7B 量级）执行改写和意图分类 |
| 多路并行召回 | ~400ms | 各路并发执行，5秒超时保护 |
| 融合 + 精排 | ~500ms | Cross-Encoder 在 CPU 上批量推理 |
| Prompt 组装 | ~50ms | 纯内存操作 |
| 首 token 延迟（LLM） | ~250ms | 流式输出，边生成边推送 |
| **首 token 到达用户** | **< 1.5s** | 上述优化的综合结果 |
| **完整答案（P50）** | **< 5s** | 取决于 LLM 生成速度 |
| **完整答案（P95）** | **< 10s** | 各路超时控制 |

### 12.2 质量基准

| 指标 | 目标值 | 含义 |
|------|--------|------|
| 召回覆盖率 Recall@20 | > 0.85 | 相关文档在 20 条召回中的覆盖比例 |
| 精排准确率 Precision@6 | > 0.70 | top-6 中与问题相关的比例 |
| 忠实度均值 Faithfulness | > 0.80 | 答案基于召回内容的比例 |
| 入库吞吐 | > 50 文档/分钟 | 批量并发入库（4 并发） |

### 12.3 关键质量杠杆

从实践经验看，以下三个环节的投入对整体质量的边际收益最高：

**文档解析与元数据增强**（决定知识库质量上限）：准确的版面识别和高质量的摘要生成是后续一切的前提，垃圾进则垃圾出。投入 LLM 生成 Chunk 摘要和关键词的算力是值得的。

**查询改写与同义词扩展**（决定召回覆盖率）：维护一份准确的领域同义词表，配合多路改写，能显著提升 BM25 召回路的覆盖率，尤其是在专业术语密集的行业领域。

**Cross-Encoder 精排**（决定精度上限）：在粗排的基础上增加精排这一步，Precision@6 通常能提升 15-25 个百分点，是提升答案准确性最直接的手段。

### 13.1 关键数据流节点说明

**PipelineContext**是两条 Pipeline 的信息总线。每个步骤从 Context 读取上游结果，将本步骤的产出写回 Context，步骤之间通过 Context 传递而非直接调用。这一设计使步骤可以独立测试、独立禁用，且 Pipeline 引擎可以统一捕获每步耗时和错误。

**MemoryManager** 在问答 Pipeline 中被 QueryUnderstandingStep（读取 Session 历史）和 PromptAssemblyStep（读取三层记忆构造 Prompt）同步调用；在答案返回给用户后，记忆更新（写入短期记忆、触发摘要压缩）通过 `asyncio.create_task` 异步执行，不增加用户等待时间。

**AdapterRegistry** 在系统启动时完成一次性的适配器实例化，之后在整个生命周期内保持单例，Pipeline 步骤在构造时注入具体的适配器实例，运行时无需再查找注册中心。

**DAG Pipeline 引擎**在执行每个步骤前检查整体超时（默认 30 秒），步骤失败时将错误写入 Context 的 errors 列表，根据配置的 stop_on_error 决定是否继续执行后续步骤。若 Context 中已存在答案（如安全过滤直接返回了拒答内容），引擎跳过所有检索和生成步骤，直接执行后处理步骤（如格式化输出）。
