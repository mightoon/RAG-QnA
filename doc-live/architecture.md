## 1. 系统定位与目标

本系统是一套**企业级私有化 RAG 智能问答框架**，定位为可复用的交付产品。其核心价值在于：

**面向客户**：将客户的私有知识（文档、数据库、业务系统）转化为可对话的智能问答能力，员工无需学习复杂的搜索技巧，直接用自然语言提问即可获得基于权威来源的准确答案，并可追溯原始文档。

**面向交付**：同一套框架代码部署到不同客户环境，只需配置文件和少量适配代码即可运行，不依赖任何特定的大模型服务商、向量数据库或认证系统，最大限度降低现场交付成本。

**文档处理工业化**：针对企业真实文档的复杂性（PDF 有文字型/扫描型/混合型/单栏双栏，Excel 有数据表和透视表，PPT 有备注）建立工业级处理流水线，每类文档有专属的处理路径和质量检测机制。

**数据一致性保障**：引入协调层（IngestionCoordinator）统管写入 MinIO、MySQL、ES、Milvus、Neo4j 五个系统的全过程，通过两阶段写入、检查点断点续写、软删除版本管理和定时一致性巡检，保障分布式写入的最终一致性。

**用户检索主权**：用户可在问答界面主动选择激活哪些检索路（向量/全文/图谱/结构化），并通过元数据筛选（文件类型/时间范围）缩小检索范围，将检索决策权从系统内部传递给用户。

系统具备以下核心能力：

- 多格式文档的自动化解析、分块与向量化入库
- 四路异构知识库的协同检索与融合排序
- 多轮对话上下文记忆与跨会话知识积累
- 答案的来源溯源与忠实度自动校验
- 完整的知识库管理与系统配置 Web 界面
- 基于角色的多租户数据隔离与权限控制

## 2. 整体架构概览

采用**共享内核（Shared Kernel）架构**，比单体框架更具有清晰的内部边界：写侧（知识库构建）和读侧（在线问答）通过稳定的内核 API 解耦，为后续独立部署留路。

### 2.1 分层结构

**当前部署形态**：模块A + 共享内核 + 模块B 在同一 FastAPI 应用中运行（单体），但内核 API 边界清晰，后续可按需拆分为独立服务（写侧和读侧在资源需求和扩缩容策略上差异显著）。

```
┌────────────────────────┐  ┌────────────────────────┐
│   模块 A：知识库构建    │  │   模块 B：在线问答      │
│  （写侧，IO密集）       │  │  （读侧，延迟敏感）     │
│  UI管理界面            │  │  对话界面               │
│  批次/任务管理         │  │  检索路选择             │
└──────────┬─────────────┘  └──────────┬─────────────┘
           │  调用内核 API               │  调用内核 API
           ▼                            ▼
┌───────────────────────────────────────────────────────┐
│                    共享内核层                           │
│                                                       │
│  IngestionKernel              RetrievalKernel         │
│  ┌──────────────────┐         ┌──────────────────┐   │
│  │ 声明式YAML Workflow│         │ QueryPlan 查询理解 │   │
│  │ 文档类型路由       │         │ 五路并行召回      │   │
│  │ 三阶段质量检测     │         │ SelfEval受控迭代  │   │
│  │ IngestionCoord.  │         │ RRF+精排          │   │
│  │ 两阶段写入        │         │ Prompt组装        │   │
│  └──────────────────┘         └──────────────────┘   │
│                                                       │
│  共享：MemoryManager | AdapterRegistry | MySQLMeta    │
└────────────────────────┬──────────────────────────────┘
                         │  标准接口契约
┌────────────────────────▼──────────────────────────────┐
│                   适配器接口层                          │
│  LLM │ Embedding │ VectorStore │ FullTextSearch        │
│  MySQLMeta │ DocParser │ KnowledgeGraph │ BusinessData │
│  Synonym │ Auth │ Storage │ EntityLinker               │
└────────────────────────┬──────────────────────────────┘
                         │
┌────────────────────────▼──────────────────────────────┐
│                  客户外部资源层                         │
│  私有LLM │ Milvus │ Elasticsearch │ MySQL(元数据)      │
│  MySQL/PG(业务) │ Neo4j/NebulaGraph │ MinIO │ Redis   │
└───────────────────────────────────────────────────────┘
```

### 2.2 两条核心数据流

系统的所有业务逻辑归结为两条相互独立的数据流：

**离线入库流****（Ingestion Pipeline）**：由管理员触发，将原始文档转化为可检索的知识表示，写入多个存储系统，是系统知识能力的来源。

**在线问答流**（Query Pipeline）：由用户触发，将自然语言问题转化为精准答案，是用户直接感知的价值。

两条流程共享底层的适配器层和外部资源层，但在编排逻辑、执行时机和性能要求上完全独立。

### 2.2 数据存储职责分工

| 存储 | 存什么 | 服务什么场景 |
|------|--------|-------------|
| MinIO | 原始文件二进制 | 答案来源溯源，原文预览 |
| MySQL（元数据库） | 文档元数据、Chunk元数据、表格结构化数据、入库任务状态 | 元数据前置过滤、入库任务管理、一致性巡检 |
| Elasticsearch | Chunk 文本全文索引（含摘要字段高权重） | BM25 关键词检索 |
| Milvus | Chunk Embedding 向量 | 语义相似度检索 |
| Neo4j/NebulaGraph | 实体节点和关系三元组 | 多跳关系推理查询 |
| MySQL（业务库） | 客户业务数据（不迁移，实时查询） | NL2SQL 结构化查询 |
| Redis | Session 状态、三层对话记忆 | 多轮对话上下文管理 |

**元数据库的特殊定位**：MySQL 元数据库不是检索路，而是检索前的**过滤层**。它先于向量库和 ES 执行，把符合条件的 chunk_id 收窄为白名单，然后向量库和 ES 在这个白名单范围内检索，大幅提升检索精度和性能。

**ES 双路索引的关键设计**：`content` 字段存正文（IK分词，走BM25），同时有 `content.kw_exact`（keyword 子字段，不分词）和独立的 `keywords`（keyword 类型，存提取的专有名词/型号）。三个字段共享存储，各自走不同查询语义，无重复存储开销。

## 3. 核心设计原则

### 3.1 不变与可换

框架的可维护性建立在一条明确的边界上：**算法逻辑不变，外部依赖可换**。

**不变的部分**构成框架的核心价值和技术护城河：Pipeline 编排逻辑、RRF 算法、Cross-Encoder 重排、三层记忆压缩、两阶段写入协议、一致性巡检规则、token 预算分配规则、可观测性埋点位置。这些内容在所有客户部署中完全一致，是系统质量的保证，不因现场情况而改变：

**可换的部分**构成系统的灵活性：所有外部服务调用通过适配器可替换（LLM、向量库、全文检索、存储）、文档解析实现（客户不同的数据格式转换逻辑）、业务规则注入（`SynonymAdapter`术语/同义词规则、`AuthAdapter`权限映射规则、`SecurityFilterStep` 合规规则及敏感词过滤等）。这些部分可以在不触碰框架核心的前提下独立替换。

### 3.2 渐进式降级

当某类外部资源不可用时，系统不崩溃，而是自动降级到更简单但仍可用的工作模式：

- 知识图谱不可用 → 跳过图谱召回路，用向量 + 关键词双路召回
- 业务数据库未连接 → 跳过结构化查询路，不影响文档问答
- Cross-Encoder 重排模型未加载 → 退回 RRF 融合得分排序
- 召回结果为空 → 明确提示知识库无相关内容，而非幻觉生成
- MySQL 元数据库不可用 → 跳过元数据前置过滤，直接进行全库检索
- 某库写入失败 → 标记 PARTIAL 状态，其他库正常可用，一致性巡检后台修复
- 所有检索路被用户关闭 → 自动回退到系统默认路（向量+BM25）

### 3.3 入库的最终一致性

写入五个存储系统的操作不可能原子化，系统采用"顺序提交+检查点+自动恢复"三机制组合，保证最终一致：即使中间任何一步失败，系统通过检查点断点续写和定时巡检自动修复，用户不需要手动干预。

### 3.4 配置即产品

从框架到可运行的客户专属系统，核心媒介是一个 YAML 配置文件（`customer_config.yaml`）。该文件描述了客户环境中所有资源的位置、凭证、参数，以及功能开关和行为参数。配置文件的变更可在不重新部署代码的情况下改变系统行为，是交付物中最重要的客户化产物。

## 4. 三大主体功能域

│  ├── 文档类型分派（PDF文字/扫描/混合 / Word / Excel / PPT…） │

│  ├── 三阶段质量检测（解析 / 分块 / 入库后验证）               │
│  └── 多库一致性写入（两阶段 / 检查点 / 软删除 / 巡检）        │
└─────────────────────┬───────────────────────────────────────┘
                      │ 知识库（Milvus+ES+MySQL+Neo4j+MinIO）

│  功能域 B：RAG 问答                                           │
│  ├── 查询理解（意图/改写/指代消解/话题跳转/子问题分解）        │
│  ├── 元数据前置过滤（MySQL，缩小检索范围）                    │
│  ├── 用户检索路选择（向量/BM25/图谱/结构化，用户主动控制）    │

└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐

## 5. 知识库构建体系

### 5.1 整体流程

入库流程是一条单向的数据处理管道，将原始文件转化为分布在多个存储系统中的结构化知识表示。整个流程由以下步骤顺序执行，每步处理上一步的输出。

```
原始文件
  ↓
  文档类型路由  →  路由到各类文档的专属处理 Pipeline
  ↓
① 文档解析      → 识别文字/表格/图片/代码，分离噪声内容
  ↓
② 多模态处理    → 图片/图表调用 VLM 生成文字描述
  ↓
③ 智能分块      → 按语义边界切分，构建父子层次 Chunk 结构
  ↓
④ 元数据增强    → 生成摘要、抽取关键词和实体、计算质量分
  ↓
⑤ Embedding     → 将摘要+关键词+正文拼接后向量化
  ↓
⑥ 并行写入      → 同时写入向量库、全文索引、知识图谱、原文存储
```

### 5.2 入库方式

系统支持四种入库方式，覆盖不同规模和场景：

**UI 拖拽上传**（适合少量文档和日常维护）：在知识库管理界面拖拽文件，单次最大 500MB，支持多文件同时提交。上传后立即触发异步入库任务，用户可在任务视图中实时查看 SSE 推送的进度。

**服务器路径指定**（适合大批量首次入库）：管理员在配置界面指定允许入库的服务器根目录（`server_ingest_root`），在 UI 填写目录路径，系统直接读取服务器挂载目录的文件，无需通过 HTTP 上传，适合几十 GB 的大批量文档。

**本地目录批量入库**：管理员在浏览器中选择本机整个目录（`<input webkitdirectory>`），JS 递归列出所有文件，以 4 并发队列逐文件上传后触发入库。扫描结果先展示预览（文件数量、类型分布、总大小），确认后才开始上传。适用于管理员本机有文档、1GB 以内的场景。

**命令行脚本**（适合 CI/CD 或定时同步）：`scripts/ingest.py` 支持目录递归扫描、并发控制、MD5 去重跳过，适合定期同步或 DevOps 场景。

所有方式统一创建 IngestBatch（单文件也建批次，total=1），任务视图提供**批次维度的聚合进度**。

### 5.3 文档类型路由与声明式 YAML 工作流

不同类型的文档在进入框架后，由文件 MIME 类型和扩展名双重判断，路由到各自的专属处理 Pipeline。

处理各类型文档的Pipeline 为声明式 YAML 工作流注册表（`workflows.yaml`），步骤序列在运行时从 YAML 加载，支持热重载。新增格式只需注册一条 workflow，不修改核心代码。

**所有 workflow 的第一步是 `detect_format`（magic bytes 文件头检测）**，防止扩展名伪装（如 XLSX 重命名为 .pdf 上传）。检测失败的文件直接拒绝入库。

以PDF 为例，系统在正式处理前先执行快速预检（`detect_scan_type`）读取前三页估算字符密度判断类型。YAML 支持**条件分支**（`condition_*` 步骤在运行时返回 `next_steps`），因此在运行时动态路由：

- 文字型 PDF：走版面分析（使用版面分析工具识别页面元素的位置和类型，区分正文段落、标题层级、表格区域、图片区域、页眉页脚，避免混排内容的错误拼接）、表格提取（有边框用 pdfplumber，无边框用列对齐检测）、图片区域截取后 VLM 理解
- 扫描型 PDF：走图像预处理（去噪/倾斜矫正/二值化）→ OCR（PaddleOCR，支持中英混排）→ 置信度评估
- 混合型 PDF：逐页判断类型，文字页走文字路径，扫描页走 OCR 路径，最终合并

PDF workflow 额外两个专项步骤：

- `extract_toc`：提取 PDF 内置书签目录（TOC），在 `outline_build` 步骤中与识别出的标题交叉验证——TOC 中有但正文未识别为标题的节点记录告警，反之亦然
- `reorder_columns`：输出 `adjacent_pair_accuracy` 指标（相邻对准确率），用于量化双栏重排质量

**Excel/CSV**：每个 Sheet 独立处理。表格的处理采用双轨策略：将表转换为"第N行：列A=值X"格式的自然语言描述入向量库/ES，同时保留原始行列结构入 MySQL table_data 表（供后续精确数值查询）。统计列的最大值/最小值/均值记录在元数据中，供元数据过滤使用。

**Word 文档**：利用文档结构模型直接提取各级标题（Heading 1/2/3）、正文段落、内嵌表格、内嵌图片，保留完整的层级结构信息作为后续分块和路径生成的依据。

**PPT**：每张幻灯片作为独立 Chunk，标题、正文、Speaker Notes 分别提取（备注往往包含最丰富的语义信息，重要性不亚于幻灯片正文）。

**图片文件**：通过 OCR 提取文字，对包含流程图、时序图、架构图等非文字内容的图片，调用多模态大模型（VLM）生成描述性文字，使图片内容进入语义检索体系。

**Markdown**：识别标题层级构建大纲树，代码块作为独立 Chunk 并标注语言类型（便于后续代码类问题的精确检索）。

### 5.3 OutlineBuilder 与 section_path

每个文档在解析阶段由 `OutlineBuilder` 维护标题栈，为每个 ParsedElement 生成 `section_path`（如 `"第三章 系统配置/3.1 网络参数配置/3.1.2 路由协议设置"`）。

PDF 通过 TOC 交叉验证标题识别的正确性；DOCX 直接读取 Word Heading 样式；Markdown 通过 `#` 数量；PPT 通过幻灯片标题框；Excel 使用 Sheet 名作一级路径。

`section_path` 的三处用途：

1. **检索过滤**：`section_path LIKE '第三章%'`（MySQL 元数据前置过滤）
2. **溯源定位**：答案来源展示 `第三章 > 3.1.2` 而非仅页码
3. **上下文聚合**：召回某 Chunk 时，可快速找到同 section 的相邻 Chunk 扩展上下文

### 5.4 智能分块策略

分块是 RAG 系统中对检索效果影响最大的工程决策。系统采用**层次化分块**而非简单的固定窗口切分：

- **父节点**代表完整的语义单元（整个段落或小节，约 2000 token 上限），包含足够的上下文，适合提供给 LLM 生成完整连贯的答案。
- **子节点**代表细粒度的语义片段（单个句子或短语，约 512 token 上限），粒度足够小，适合精确定位和相关性计算。

检索时使用子节点定位最相关的细粒度内容，但喂给 LLM 时取回对应的父节点完整内容，兼顾检索精度和生成质量。

分块边界的选取遵循优先级：标题边界 > 段落边界 > 句子边界 > 固定 token 数截断。

#### 确定性 chunk_id（幂等写入）

`chunk_id = sha256(tenant_id:doc_id:seq:content_hash[:8])[:32]`

同一文档重新入库时，相同位置和内容的 Chunk 产生相同 chunk_id，ES 和 Milvus 的 upsert 操作直接覆盖旧数据，无需额外删除逻辑，大幅简化一致性保障的实现复杂度。

### 5.5 元数据增强

元数据增强是入库阶段 ROI 最高的工程投入。每个子 Chunk 在写入存储前，系统会并发执行以下增强操作：

- **摘要生成**：调用轻量 LLM 生成 1-2 句核心内容摘要（约 100 字），摘要与正文拼接后一起 Embedding，使向量同时捕获关键信息和细节内容；摘要在后续检索时也用于上下文压缩
- **关键词抽取**：提取 top-10 专业关键词，写入全文索引的专用字段（检索权重高于正文）
- **实体识别**：抽取人名、产品名、组织名等命名实体，用于知识图谱写入和图谱召回路的实体锚定
- **质量评分**：评估 Chunk 的信息密度（中文内容占比、噪声符号占比等），低质量 Chunk 在召回时会被过滤

文档大纲与 Chunk-章节关系

`OutlineBuilder` 在解析阶段维护标题栈，为每个 ParsedElement 生成 `section_path`（如 `"第三章 系统配置/3.1 网络参数配置/3.1.2 路由协议设置"`）。此路径存入 `chunks_meta.section_path` 字段，用于：① 元数据前置过滤（`section_path LIKE '第三章%'`）；② 溯源定位展示；③ 同章节 Chunk 聚合扩展上下文。

### 5.6 异步任务生命周期

```
PENDING（提交等待）
  ↓ 调度器取出
PARSING（文档解析中）  ← 推送进度：第N/M页
  ↓
CHUNKING（分块增强中）  ← 推送进度：已生成N个Chunk
  ↓
EMBEDDING（向量化中）
  ↓
WRITING（写入各库中）   ← 每库完成后更新 checkpoint
  ↓
DONE ─────────────────→ 触发完成通知（UI/邮件/Webhook）
PARTIAL（部分库失败）  ← 可降级使用，巡检后台修复
FAILED（已用尽重试）  ─→ 触发失败通知

任何阶段失败 → RETRYING（指数退避：1min/5min/15min，最多3次）
```

**幂等性保障**：提交时计算文件 MD5，若同内容文档已存在且状态为 DONE，直接返回已有任务，跳过处理。状态为 FAILED 的文档允许重新入库（覆盖）。

**断点续写**：每个库写入完成后在 MySQL 的 checkpoint 字段打钩（`{"minio":true,"mysql":true,"es":false,...}`）。重试时从检查点之后继续，不重复已完成的库。

### 5.7 两级任务模型

```
IngestBatch（批次）
  ├── batch_id
  ├── total / succeeded / failed / pending
  ├── status（pending/running/done/partial_failed）
  └── IngestTask × N（子任务，每个文件一个）
        ├── task_id → batch_id 外键
        ├── status（PENDING→PARSING→...→DONE/FAILED）
        ├── WriteCheckpoint（各库写入进度，断点续写用）
        └── quality_summary

```

任务视图提供两级视图切换：**批次视图**（"这批200个文件中已完成180个，失败3个"）和**任务视图**（展开某批次查看每个文件的详细状态）。

### 5.8 三阶段质量检测

**解析后检测（ParseQualityCheckStep）**：

| 检测项 | 判断标准 | 处理动作 |
|--------|----------|----------|
| 文字提取率 | < 20% | 标记需要 OCR 补充 |
| OCR 置信度 | < 0.6 | 标记该页为低质量，在质量报告中记录告警 |
| 乱码率 | > 5% | 尝试重新编码，失败则记录告警 |
| 空白页比例 | > 30% | 质量报告告警 |

**分块后检测（ChunkQualityCheckStep）**：

| 检测项 | 判断标准 | 处理动作 |
|--------|----------|----------|
| 信息密度 | < 0.3 | quality_score 调低，检索时降权 |
| 过短 Chunk | token < 20 | 合并到相邻 Chunk |
| 同文档重复 | 余弦相似度 > 0.95 | 标记 duplicate，跳过入库 |

**入库后验证（PostWriteVerificationStep）**：抽样 6 个 Chunk，在 ES 和 Milvus 中各回查，验证写入正确性。验证失败触发局部补写（只补写失败的 Chunk）。

系统**永远不因质量问题阻塞入库（不 pending 等待人工）**。低质量情况的处理策略：

- 轻度问题（置信度 0.6-0.8）→ 告警+降权；
- 中度问题（置信度 0.4-0.6）→ 告警+建议重传；
- 严重问题（置信度 <0.4 或全文字符<100）→ 标记 `PARTIAL` 状态，对应 Chunk `quality_score=0.1`（检索时几乎不被召回）。

管理员通过质量报告界面知晓后可选择重新上传。

### 5.8 四库写入顺序与依赖关系

写入顺序严格按依赖关系排列，不可调换：

```
① MinIO（原文件）
       ↓ storage_url 确定后
② MySQL（documents + chunks_meta + table_data）
       ↓ chunk_id 在 MySQL 中存在后
③ ES（全文索引，按 chunk_id 检索）
④ Milvus（向量索引，按 chunk_id 检索）
       ↓ 可选
⑤ Neo4j/NebulaGraph（知识图谱）
```

每步完成后更新 MySQL checkpoint，确保故障恢复时可从断点续写。

## 6. 在线问答引擎

### 6.1 完整处理流程

```
用户输入（含检索路选择 + 元数据筛选）
  ↓
① 安全过滤          → 敏感词/注入/权限校验
  ↓
② 查询理解 → QueryPlan
   ├── 实体识别 + EntityLinker（原始名 → 规范名/canonical）
   ├── 约束提取（时间/类型 → QueryConstraint，硬下推不参与相关性）
   ├── 隐式元数据意图（ImplicitMetaExtractor）
   ├── 同义词扩展（SynonymAdapter）
   ├── 软路由权重（每路 0-1 浮点数，替代布尔开关）
   └── 语义句构造（剥离约束+实体的纯语义核心）
  ↓
③ 元数据前置过滤    → MySQL chunk_id 白名单（显式+隐式合并，section_keyword支持）
  ↓
④ 五路并行召回（独立5s超时，QueryPlan.constraints 统一下推到所有路的filter）
   ├── KW_EXACT：ES content.kw_exact + keywords 字段 term 精确匹配
   ├── VECTOR：Milvus 向量检索（semantic_query + rewrites）
   ├── BM25：ES text 全文检索（同义词扩展词降权合并）
   ├── GRAPH：图谱多跳推理（entities.canonical 定位节点）
   ├── STRUCTURED：NL2SQL（plan.constraints 辅助WHERE生成）
   └── EPHEMERAL：临时文档检索（始终激活，分数×1.2）
  ↓
⑤ RRF 融合（route权重参与融合系数）+ 语义去重
  ↓
⑥ 受控迭代自评（SelfEvalStep）
   └── 最高分 < 0.5 且未超迭代上限(2) → 触发失败导向改写 + HyDE，二轮结果合并
  ↓
⑦ Cross-Encoder 精排（top-40→top-6）
  ↓
⑧ Prompt 组装（记忆注入 + 上下文压缩 + 引用编号 + figure_label 溯源）
  ↓
⑨ LLM 流式生成
  ↓
⑩ 忠实度校验 + 来源溯源（figure_label优先）+ 格式化输出
```

### 6.2 查询理解子系统

查询理解是整个在线流程中对召回质量影响最大的单一环节。用户的自然语言提问和知识库文档的书面表达之间存在固有的词汇鸿沟，查询理解的核心任务是弥合这个鸿沟。

**意图分类**将问题划分为六类：事实查询（Factual）、关系推理（Relational）、聚合统计（Aggregation）、步骤流程（Procedural）、对比分析（Comparative）、闲聊（Chitchat）。意图类型直接决定后续路由到哪些召回路——闲聊直接由 LLM 生成，无需检索；聚合统计路由到 NL2SQL；关系推理激活图谱路。

**指代消解**处理多轮对话中的代词和省略：将"它支持多少端口？"还原为"X300 交换机支持多少端口？"，将"那第二条呢？"还原为完整的独立问题。这一步骤是多轮对话场景下召回准确性的关键前提。

**Standalone 补全**将当前轮的问题（可能是追问、省略主语的问题）改写为一个完整的、无需上下文即可理解的独立查询，用于后续的向量化和检索。

**话题跳转检测**通过计算当前问题向量与工作记忆中话题向量的余弦相似度，判断用户是否切换了话题。检测到跳转时重置话题相关的实体槽位，避免旧话题的上下文污染新话题的检索。

**复合问题分解**将"比较 A 和 B 的价格、性能和售后"这类复合问题分解为多个原子子问题，分别检索后在生成阶段合并，解决单一检索无法覆盖多维度问题的问题。

### 6.3 QueryPlan：结构化查询计划

查询理解的产物是结构化 `QueryPlan`，把用户问题分解为五个互不干扰的层次分别投放到对应检索路：

| 层次                 | 内容                   | 投放路径                            |
| -------------------- | ---------------------- | ----------------------------------- |
| `constraints`        | 时间/类型/部门等硬约束 | 所有路的 filter（不参与相关性计算） |
| `entities.canonical` | 实体归一化规范名       | kw_exact 精确匹配                   |
| `keywords`           | 专有名词/型号/编号     | kw_exact + BM25                     |
| `semantic_query`     | 剥离约束后的纯语义核心 | VECTOR 向量化                       |
| `synonyms`           | 同义词扩展             | BM25 降权合并                       |

约束做硬过滤、实体走精确、关键词走词面、语义走向量、同义词降权合并——各类信息互不干扰，精度和覆盖率均优于单一查询文本的全库检索。

### 6.4 用户检索路选择

检索路的控制权从系统内部（只有意图路由决定）传递给用户：

**系统层面**（管理员在配置界面设定）：哪些检索路物理上可用（有没有接向量库？有没有接图谱？）。这是硬上限，用户无法突破。

**用户层面**（用户在问答界面设定）：在系统允许的范围内，用户可以独立开启或关闭每条检索路。选择存入 localStorage，跨 Session 记住偏好。

最终激活的检索路 = 系统启用路 ∩ 用户选择路。

### 6.5 EntityLinker 实体归一化

用户说"华为"，文档存的是"华为技术有限公司"；用户说"合规部"，知识库里是"合规与法务部"。不做实体归一化，kw_exact 路就无法精确命中。

EntityLinker 两阶段匹配：规则阶段（O(n) 字符串匹配 MySQL 实体列表，毫秒级）→ 向量阶段（向量近邻，仅规则未命中时触发）。命中阈值 0.88，低于此值不归一化，保留原始名称走 BM25 模糊匹配。

### 6.6 受控迭代查询（SelfEvalStep）

首轮融合结果的最高相关性分数若低于阈值（默认 0.5），且未超过迭代上限（默认 2 轮），SelfEvalStep 自动触发第二轮：

- **失败导向改写**：提示 LLM"上轮未找到足够相关内容，请换角度措辞"
- **HyDE**：让 LLM 生成假设性回答文档，以该文档为向量查询

二轮结果与首轮合并去重（取分数最高版本），再走精排。普通查询直通（无额外延迟），触发时增加约 800-1500ms。最多 2 轮，防延迟失控。

### 6.7 元数据前置过滤层

MySQL 元数据库不是检索路，而是检索前的**过滤层**，先于所有检索路执行，把候选 Chunk 收窄为 chunk_id 白名单（上限 50000），再把白名单作为 filter 注入所有检索路。

过滤条件来源两路合并（显式优先）：

- **显式**：用户在 UI 检索路面板设置（文件类型/时间范围/知识域）
- **隐式**：ImplicitMetaExtractor 从问题语义推断（"去年Q3" → 时间范围，"第三章" → section_path 前缀）

### 6.8 软路由权重

软路由为 0-1 浮点权重控制，影响 RRF 融合时各路的系数。

意图基础权重示例：

- `factual`（事实查询）→ kw_exact=0.9, bm25=0.9, vector=0.8, graph=0.0
- `relational`（关系查询）→ vector=0.7, graph=0.9
- `aggregation`（统计查询）→ structured=1.0, others=0.1

权重在意图基础上还受实体类型（有精确实体则提升 kw_exact）和约束（有时间约束则提升 structured）动态调整，最后与用户 UI 选择取交集（用户关闭的路权重置 0）。

### 6.9 多路并行召回

五路召回基于各自不同的检索原理，互补覆盖不同类型的信息需求，且并发执行以控制延迟。

**向量语义召回**：将 Standalone 查询及其多路改写版本分别向量化，在向量库中执行 ANN（近似最近邻）检索，每路取 top-20 结果后合并去重。这一路的优势是语义理解能力——即使用词不同，只要含义相近就能命中；劣势是对精确术语（型号、代码）的召回不稳定。

**BM25 关键词召回**：对改写后的查询在 Elasticsearch 中执行全文检索，同时匹配正文字段（权重 1.0）和摘要字段（权重 1.5）。BM25 在精确术语匹配上天然更稳健，与向量召回形成互补。

**知识图谱召回**：从问题中提取命名实体，在图谱中定位对应节点，然后做 1-3 跳的关系遍历，返回实体间的关系链路并序列化为自然语言。这一路专门处理多跳关系问题，是向量和 BM25 无法处理的盲区。

**结构化数据召回**：将自然语言问题转换为 SQL（NL2SQL），查询客户的业务数据库，返回精确的数值、统计或记录。用于处理"上个季度的销售额是多少"这类需要实时数据的聚合统计类查询。

每路召回都有独立的超时控制（默认 5 秒），某路超时只记录警告，不阻塞其他路的结果返回。

| 检索路     | 底层引擎          | 擅长场景                    | 劣势                     |
| ---------- | ----------------- | --------------------------- | ------------------------ |
| KW_EXACT   | ES keyword        | 型号/编号/专有名词精确匹配  | 无语义理解               |
| VECTOR     | Milvus            | 语义/意图/近义词/口语化查询 | 精确关键词不稳定         |
| BM25       | ES text           | 关键词自然语言、中文分词    | 词汇鸿沟（近义词覆盖差） |
| GRAPH      | Neo4j/NebulaGraph | 多跳关系推理                | 实体识别误差放大         |
| STRUCTURED | MySQL/PG          | 聚合统计、数值查询          | 仅覆盖结构化数据         |

KW_EXACT 和 BM25 同为 ES，但查询语义根本不同：前者不分词（完整匹配），后者分词（模糊匹配）。分开作为独立路，用户可单独控制，路由权重也独立计算。

### 6.10 融合与重排子系统

多路召回的结果处于不同的量纲体系（向量余弦相似度 0-1；BM25 分数无上界），需要统一融合和精排后才能作为 Prompt 上下文。

**RRF 融合（倒数排名融合）**：不依赖各路的原始分数，只依赖排名，为每个文档计算 `Σ 1/(rank_i + 60)` 的融合分数，天然解决量纲不一致问题。这一步将所有路的结果合并为一个统一排名列表（约 40 个候选）。

**语义去重**：融合列表中可能存在内容高度重叠的 Chunk（同一原文的不同版本，或父子节点）。通过计算两两余弦相似度，语义相似度超过阈值（0.92）的 Chunk 只保留得分更高的一个，避免上下文中充斥重复信息。

**Cross-Encoder 精排**：对去重后的 top-40 候选，使用 Cross-Encoder 模型（如 BGE-Reranker）对每个（查询, 候选文本）对联合建模打分（0-1）。Cross-Encoder 的精度显著高于向量相似度（因为它是联合建模而非独立向量的点积），低于阈值（0.3）的候选被过滤，最终保留 top-6 进入 Prompt。

### 6.11 Prompt 构造与生成

**Prompt 组装**将记忆层信息、检索结果、用户问题按固定结构拼接，总 token 预算约 7000：

- System Prompt（角色定义、引用格式要求）：约 300 token，固定
- 用户画像（专业背景、偏好格式）：约 200 token，从长期记忆加载
- 工作记忆（对话摘要、已确认实体）：约 400 token，每轮更新
- 短期记忆（最近 3-5 轮完整 Q&A）：约 1500 token，动态裁剪
- 检索上下文（top-6 Chunk，各带编号标签）：约 4000 token，本轮检索
- 当前问题（Standalone 补全版本）：约 200 token

排列顺序遵循"最相关内容放首位"原则，规避 LLM 对中间内容注意力衰减的问题（Lost in the Middle 效应）。

**来源溯源**通过引用编号绑定实现：每个 Chunk 在 Prompt 中标注 `[文档1]`、`[文档2]` 等编号，并要求 LLM 在关键陈述后引用来源编号，生成后系统解析引用关系，将编号映射回实际文档和页码，供用户点击查看原文。

**图片溯源**：`FigureLabelExtractor` 在版面分析阶段检测图片下方紧邻的短文本块，用正则识别"图28 / Figure 3-2 / 表5"等标注，存入 `raw_data.figure_label` 和 `raw_data.figure_caption`。答案溯源时展示优先级：`figure_label`（"图28"）> `figure_caption`（图题文字）> `page_num`（"第12页"）。

**忠实度校验**在生成完成后，用 LLM 对答案和召回文档做一轮独立评判，输出 0-1 的忠实度分数。低于阈值（0.6）时在答案末尾追加免责声明，明确提示用户该答案的部分内容超出知识库范围。

### 6.12 Session 临时文档

用户在对话框上传临时文档后，系统走轻量化处理路径（跳过 VLM 图片理解、实体抽取，只做基础解析+固定窗口分块+向量化），控制在 30 秒内完成，写入 Session 专属的临时 collection（`tmp_{session_id}`）。

临时文档的 RRF 分数乘以 1.2 加权系数，在融合排序中优先于全局知识库。2 小时后 TTL 到期，Milvus 自动清理对应 collection。

## 7. 多轮对话记忆体系

### 7.1 三层记忆架构

多轮对话的核心矛盾是：LLM 的上下文窗口有限，但用户的对话历史无限增长。系统用三个粒度不同的记忆层次解决这个矛盾，各层在信息密度和持久性上形成梯度。

```
短期记忆（In-Context）
  最近 3-10 轮的完整 Q&A，直接放入 Prompt
  存储：动态维护在 Session 状态中（Redis）
  特点：完整准确，但容量受 token 预算限制
         ↓ 超出上限时压缩
工作记忆（Session Summary）
  对话摘要 + 实体槽位 + 话题链路
  存储：Redis，与 Session 状态同存
  特点：压缩态，信息密度高，捕获关键约束和已确认事实
         ↓ Session 结束时归档
长期记忆（Cross-Session）
  用户画像 + 历史 Session 摘要向量 + 纠错记录
  存储：关系数据库（用户画像）+ 向量库（摘要检索）
  特点：跨会话持久化，在新 Session 开始时加载
```

### 7.2 记忆的流转机制

**短期记忆的滚动压缩**：当短期记忆超过 token 阈值（约 1500 token）时，系统将最早的若干轮从短期记忆中弹出，通过异步 LLM 调用将被弹出内容合并到工作记忆的滚动摘要中，同时从 Prompt 中移除那些轮次的原文。这一过程在答案返回后的后台异步执行，不影响主链路延迟。

**实体槽位的持续更新**：系统维护一个结构化的实体状态字典，记录对话中出现并被确认的关键实体（当前产品型号、用户角色、约束条件、待确认事项），每轮对话后异步更新。槽位信息直接用于 Standalone 补全（补入省略的主语）和路由决策（已知产品型号时直接精确匹配）。

**话题链路追踪**：工作记忆中维护话题跳转路径（如"产品选型 → 技术规格 → 网络配置 → 故障排查"），用于判断当前意图的话题域归属，并作为检索过滤条件缩小召回范围。

**Session 归档**：用户结束对话或超过无活动时限后，系统触发归档流程：生成本 Session 的完整摘要，向量化后写入用户专属的长期记忆向量空间，同时更新用户画像（专业背景、偏好格式、常用产品、纠错记录）。下次对话开始时，用新问题在历史 Session 中检索最相关的历史上下文注入 Prompt。

### 7.3 话题跳转的处理

当检测到用户切换话题时，系统执行选择性记忆重置：清除话题相关的实体槽位（当前话题、待确认事项）和话题向量，但保留用户身份信息和跨话题稳定的约束（如用户角色、设备型号）。这避免了旧话题的上下文污染新话题的检索，同时保留了对用户身份的持续理解。

### 7.4 用户反馈改善机制

三条闭环路径：

1. 即时影响：同 Session 内将负反馈注入短期记忆，LLM 感知后调整策略；
2. 检索权重优化：定时任务分析高频负反馈 Chunk，自动调整 `quality_score`（±0.05-0.1）；
3. 意图分类优化：运营人员定期审查路由错误的反馈，补充到意图分类 few-shot 示例中。

## 8. 适配器层与外部资源集成

### 8.1 适配器模式的本质

适配器层是系统框架化交付的技术基础。它在框架编排核心和外部资源之间建立了一层标准化接口，使核心逻辑对具体的外部服务实现无感知。

每类外部资源对应一个抽象基类（接口契约），定义该类资源的标准操作集合。框架核心只调用抽象基类的方法，不依赖任何具体实现。不同客户环境中的具体服务（不同厂商的 LLM、不同品牌的向量库）通过继承基类并实现其方法来接入框架，对框架核心完全透明。

### 8.2 适配器类型

系统定义11类适配器，覆盖所有外部依赖：

**LLM 适配器**负责与大语言模型推理服务的交互，提供文本生成（流式和非流式）、token 计数、以及系统自用的高层能力（查询改写、意图分类、摘要压缩、忠实度评估）。框架默认实现兼容 OpenAI Chat Completions API 格式，可通过配置对接任何提供该格式接口的服务，包括国产模型的 OpenAI 兼容端点和本地部署的 vLLM 服务。

**MySQL 元数据适配器**：独立于业务数据适配器，专门管理系统自身的元数据。核心方法包括：文档和 Chunk 元数据的 upsert/查询，元数据过滤查询（`query_chunk_ids`，返回符合条件的 chunk_id 白名单），入库任务的 CRUD，一致性巡检辅助查询。自动建表（DDL 幂等，首次启动时执行）。

**Embedding 适配器**将文本转化为固定维度的向量表示，支持批量处理，并为 BGE 系列模型提供查询前缀注入（显著提升检索效果）。入库和检索必须使用完全相同的适配器实例，以确保向量空间的一致性。

**向量库适配器**封装向量数据库的写入、检索、删除操作，支持基于元数据的过滤条件（权限、时间范围、所属 collection），并能按 doc_id 批量删除（知识更新时使用）。内置 Milvus、Qdrant、pgvector 三种实现。

**全文检索适配器**封装 BM25 全文检索操作，定义包含内容字段、摘要字段（高权重）、关键词字段的索引结构，支持中文 IK 分词器配置。内置 Elasticsearch 和 OpenSearch 两种实现。

**文档解析适配器**按文件类型路由到对应的解析实现，输出统一格式的结构化文档对象（元素列表，含类型、文本、坐标等）。内置 PDF、DOCX、图片（OCR）三种解析器。

**业务数据适配器**提供自然语言到 SQL 的转换、SQL 安全校验、查询执行和结果脱敏能力，Schema 描述通过 YAML 文件配置，支持 any SQLAlchemy 兼容的关系数据库。

**知识图谱适配器**提供实体查找、多跳关系遍历、实体和关系的写入能力，以及将图查询结果序列化为自然语言的 to_text 方法。内置 Neo4j 和 NebulaGraph 两种实现，两者在查询语言（Cypher vs nGQL）和连接协议（Bolt vs Thrift）上存在差异，均通过各自的适配器封装，对框架核心完全透明。

**同义词适配器**提供术语扩展（一个词映射到所有同义词）和术语归一化（将口语替换为知识库中的标准术语）。支持从 Excel 或 YAML 文件热加载，也可对接客户的专有术语 API 服务。

**认证权限适配器**验证用户身份 Token，返回包含用户 ID、角色列表、租户 ID 的用户上下文，供后续的权限过滤使用。内置 JWT 和 OIDC（标准协议）两种实现。

**对象存储适配器**管理原始文件和多媒体内容的存储，提供上传、下载、删除和生成临时预览 URL 的能力。内置 MinIO（S3 兼容）和本地文件系统两种实现。

### 8.3 适配器注册机制

框架提供一个中央注册中心（AdapterRegistry），在系统启动时将所有适配器类（含内置和客户自定义）按名称注册。配置文件中通过 `adapter: "名称"` 字段指定使用哪个实现，注册中心在运行时动态实例化对应的类并注入配置。这一机制使得在不修改任何框架代码的前提下，通过修改配置文件即可切换底层服务。

### 8.4 适配器完整清单

| 类型           | 注册名                            | 内置实现 | 用途                     |
| -------------- | --------------------------------- | -------- | ------------------------ |
| LLM            | openai_compatible / vllm          | ✓        | 文本生成、查询改写、摘要 |
| Embedding      | http_embedding / openai_embedding | ✓        | 向量化                   |
| VectorStore    | milvus / qdrant / pgvector        | ✓        | 语义检索                 |
| FullTextSearch | elasticsearch / opensearch        | ✓        | BM25 检索                |

| DocParser      | pdf / docx / image                | ✓        | 文档解析                 |
| BusinessData   | sqlalchemy                        | ✓        | NL2SQL                   |
| KnowledgeGraph | neo4j / nebula                    | ✓        | 关系推理                 |

### 8.5 客户资源对接分类

客户现场的对接工作按复杂度分为三类：

**纯配置**（0 行代码）：客户使用的服务恰好在框架内置列表中（如 Milvus、Elasticsearch、OpenAI 兼容接口、OIDC 认证），只需在 YAML 文件中填写连接信息和凭证。

**适配器实现**（50-200 行代码）：客户使用的服务框架未内置（如私有 RPC 格式的 LLM 接口、非标准认证系统、工业图纸解析），需继承对应抽象基类实现若干方法，工作量通常在 1-4 天以内。

**资源禁用**（1 行配置）：客户没有某类资源（如无知识图谱），在配置中设置 `enabled: false`，对应的召回路自动跳过，系统降级运行。

## 9. 多库数据一致性体系

### 9.1 一致性挑战

一个文档入库需要写入五个系统（MinIO→MySQL→ES→Milvus→Neo4j），这五次写入不在同一事务中。常见故障场景：进程在 ES 写入后崩溃，Milvus 数据缺失；文档更新时旧版本删除后新版本写入一半失败。

### 9.2 两阶段写入协议

IngestionCoordinator 将写入过程分为两阶段：

**阶段一**（解析/分块/Embedding）：纯计算，无外部写入，失败重试成本低。

**阶段二**（顺序写入）：按依赖顺序逐库写入，每步完成后在 MySQL `WriteCheckpoint` 字段打钩。故障恢复时读取 `WriteCheckpoint`，从第一个 false 的库开始续写，已完成的库不重复写入（ES 和 Milvus 均支持 upsert 语义，重复写入安全）。

### 9.3 软删除版本管理

文档更新（覆盖入库）时不直接删除旧版本：

1. 旧版本标记为 `SUPERSEDED`（数据仍在各库中）
2. 新版本入库（checkpoint 全部完成）
3. 异步清理旧版本（从 ES/Milvus 删除旧 chunk_id，MySQL 级联删除）

这保证了在新版本写入期间，旧版本持续可用，用户不会经历"文档消失"的窗口期。

### 9.4 定时一致性巡检

每小时执行一次巡检（`ConsistencyCheckConfig` 配置）：取最近 100 个 DONE 文档，对比 MySQL 中的 chunk_id 集合与 ES、Milvus 中的实际数据，发现差集则自动补写。巡检发现的不一致数量和修复操作数量写入监控指标，差异超阈值时告警。

## 10. 用户界面体系

### 10.1 技术定位

前端界面采用无构建步骤的技术方案：原生 HTML + CSS + Vanilla JavaScript，以 Alpine.js 处理响应式交互逻辑，由 FastAPI 后端直接托管静态文件和 Jinja2 服务端渲染模板。这一选择的核心理由是现场部署简单——无需 Node.js、无需 npm 构建，复制文件即可运行，与框架整体"降低交付成本"的目标一致。

### 10.2 三个核心界面

#### 10.2.1 聊天对话界面

用户的主要使用入口，采用三栏布局：左侧侧边栏展示历史会话列表，中间主区为对话消息流，右侧可展开引用来源抽屉。

核心交互细节：

- 消息区域支持 Markdown 渲染和代码块语法高亮；
- AI 回答中的引用编号（如 `[文档1]`）可点击，展开显示原始文档标题、章节、页码和预览链接；
- 输入框支持 `Enter` 发送和 `Shift+Enter` 换行；
- AI 生成过程中实时流式展示 token，支持用户随时点击停止；
- 新建会话、历史会话切换、会话重命名和删除均在侧边栏完成；
- 多个知识域（collection）时显示知识域选择器，用户可选择在特定知识范围内提问；
- 折叠式检索路选择面板（向量/全文/图谱/结构化，开关独立）
- 元数据筛选器（文件类型/时间范围，可选，影响 MySQL 前置过滤）
- "本次对话文档"上传区（临时文档上传，仅本 Session 有效）
- 检索路偏好存 localStorage，跨 Session 记忆

#### 10.2.2 知识库管理界面

面向管理员，提供文档的完整生命周期管理

- 支持拖拽上传（PDF/Word/TXT/图片），上传后自动触发入库 Pipeline，通过进度条实时显示入库任务状态（等待、处理中、成功、失败）；
- 文档列表展示文件名、文件类型、Chunk 数量、大小和入库时间，支持按 collection 切换视图；
- 支持单文档删除（同步清除向量库、ES 和图谱中的所有相关 Chunk）、批量删除和重新索引（覆盖已有 Chunk）；
- 顶部统计卡实时展示当前 collection 的文档总数和 Chunk 总数；
- 视图切换：文档列表 / 任务列表
- 任务列表：状态机展示，SSE 实时进度（EventSource，非轮询）
- 手动重试按钮（仅 FAILED 状态）
- 质量报告弹窗（高/中/低质量 Chunk 分布，OCR 置信度，告警列表）
- 服务器路径入库选项卡（需配置 server_ingest_root）

#### 10.2.3 系统配置界面

面向系统管理员，通过四个 Tab 组织所有配置项：

- **资源连接 Tab**：展示所有外部资源（LLM、向量库、ES、MySQL 元数据库、图谱、对象存储、Redis、业务数据库）的连接配置表单，每个资源块末尾提供"测试连接"按钮，实时显示连接状态（正常/失败/未启用）
- **功能开关 Tab**：以 Toggle 控件展示各召回路（向量、BM25、图谱、结构化）和 Pipeline 步骤（图片理解、重排、忠实度校验）的启用状态，提供召回参数（top_k、重排阈值）的数值调整
- **知识域权限 Tab**：表格形式展示角色到 collection 的映射，支持新增、编辑和删除权限条目
- **提示词 Tab**：System Prompt 的富文本编辑，以及意图分类 few-shot 示例的增删改

配置界面内置变更追踪：

- 有未保存更改时顶栏显示提示，提供"撤销更改"按钮恢复到上次保存状态；
- 保存时敏感字段（API Key、密码）若用户未修改则保留原值，不因界面操作被清空。

### 10.3 前后端交互模式

界面与后端的交互采用两种模式：

**SSE 流式问答**：用户发送问题后，浏览器向后端建立 Server-Sent Events 连接。后端依次推送三类事件：检索完成后立即推送来源列表（用户看到引用来源），然后逐 token 推送生成内容，最后推送完成信号（含 session_id 和 AI 自动生成的对话标题）。这一设计使用户在等待生成时即可看到答案的依据来源，提升可信度感知。

**REST API**：其余操作（会话管理、文档管理、配置读写、连接测试）均通过标准 RESTful JSON 接口交互，接口由框架的 FastAPI 路由层提供。

### 10.4 关键交互设计

**检索路选择器的可用性逻辑**：未在系统配置中启用的检索路显示为灰色且不可勾选，并标注"未配置"，避免用户误操作后无法理解为什么选项不生效。

**任务进度的 SSE 实时推送**：知识库界面对进行中的任务订阅 SSE EventSource（`/api/v1/ingest/tasks/{id}/progress`），服务端在每个阶段变更时推送事件，前端实时更新进度条和阶段描述，无需轮询。

**质量报告的可视化**：高/中/低质量 Chunk 以比例条形图展示（非列表），使管理员能快速判断整体质量水平，而不是淹没在数字中。

## 11. 安全与权限体系

### 11.1 多层安全防护

系统在多个层次实施安全控制，从外到内依次为：

**输入安全**（SecurityFilterStep）：问答 Pipeline 的第一步，强制执行敏感词过滤、Prompt 注入检测（识别"忽略之前的指令"等注入模式）、查询长度限制，任一检测命中则立即终止后续步骤，直接返回安全提示。

**认证安全**（AuthMiddleware）：所有 API 请求在到达业务逻辑之前通过认证中间件，验证 Bearer Token 并提取用户上下文（user_id、roles、tenant_id）。Token 验证委托给 AuthAdapter，支持 JWT 自签和 OIDC 单点登录两种模式。

**权限过滤**（数据库查询层）：用户的角色列表通过配置文件映射为可访问的 collection 白名单，这个白名单在每次检索时作为硬性过滤条件注入向量库和 ES 的查询中，在数据库层面执行过滤，而非在应用层过滤，从根本上防止越权数据泄露。

**数据隔离**（tenant_id）：向量库和全文索引的所有读写操作必须携带 tenant_id，租户之间的数据在同一物理集群中逻辑隔离，互不可见。

**SQL 安全**（BusinessDataAdapter）：NL2SQL 生成的语句在执行前必须通过白名单校验（只允许 SELECT，只允许访问配置中声明的表），并对结果中的敏感字段（手机号、身份证号等）自动脱敏。

### 11.2 知识域权限模型

系统采用基于角色的知识域访问控制（RBAC on Collections）：

- 知识库按业务属性划分为若干 collection（如技术文档、HR 文档、销售案例）
- 每个角色被授权访问特定的 collection 集合（`*` 代表全部）
- 权限映射在配置文件中声明，可通过配置界面动态编辑
- 文档入库时可指定 `allowed_roles` 限制访问范围
- 检索时以用户角色和知识域白名单的交集作为过滤条件

这一模型支持灵活的权限场景：运维工程师只能看到技术文档，HR 只能看到 HR 文档，管理员可看到全部。

## 12. 可观测性与运维体系

### 12.1 可观测性三支柱

系统的可观测性覆盖日志、指标和追踪三个维度，通过标准化接口对接客户现有的监控平台：

**结构化日志**：使用 structlog 输出 JSON 格式日志，每条日志携带 session_id、tenant_id、step_name 等上下文字段，便于在日志平台（ELK、Splunk 等）中按维度过滤和分析。

**Prometheus 指标**：定义一套标准指标集，指标推送到 Prometheus Push Gateway，通过 Grafana 可视化。涵盖：

- 查询总次数（按意图类型和状态分）、各 Pipeline 步骤延迟分布、召回分数分布、知识库 Chunk 总数、活跃 Session 数。
- `rag_ingest_tasks_total{status}` — 入库任务总量按状态分类
- `rag_ingest_duration_seconds{stage}` — 各入库阶段耗时分布
- `rag_consistency_issues_total` — 一致性巡检发现的问题数量
- `rag_consistency_repairs_total` — 自动修复的数量
- `rag_ephemeral_docs_active` — 当前有效的临时文档数量
- `rag_chunk_quality_score{bucket}` — Chunk 质量分布（高/中/低）

**OpenTelemetry 链路追踪**：每次请求生成一个 Trace，每个 Pipeline 步骤作为一个 Span，包含步骤名称、耗时、召回数量、错误信息等属性。支持导出到 Jaeger 或其他 OTLP 兼容的追踪后端，用于定位延迟瓶颈和排查错误。

### 12.2 知识库质量运维

系统提供批量入库脚本和评测脚本两个运维工具：

**批量入库脚本**（`scripts/ingest.py`）支持单文件和目录批量入库，并发控制（默认 4 并发），按文件 MD5 去重（内容未变则跳过），实时显示入库进度和 Chunk 数量，入库完成后汇总统计成功/失败数量。

**评测脚本**（`scripts/evaluate.py`）基于预定义的测试问题集（YAML 格式，包含问题和参考答案），批量运行完整问答流程，计算三项核心质量指标：忠实度均值（Faithfulness，衡量答案是否基于召回内容）、召回率（Recall@20，衡量相关文档是否被召回）、平均延迟和 P95 延迟。评测结果输出为 JSON 报告，是调优分块策略、同义词表和召回参数的数据依据。

### 12.3 运维管理 API

系统提供以下运维 API 供管理界面调用：

- **全组件健康检查**：逐一调用所有适配器的 health_check()，返回各组件状态和延迟
- **知识库统计**：查询各 collection 的文档数和 Chunk 数
- **文档删除**：从向量库、ES 和图谱级联删除指定文档的所有数据
- **同义词热重载**：无需重启服务，即时更新同义词表
- **入库任务状态查询**：通过 task_id 轮询异步入库任务的处理进度
- **连接测试**：对指定组件的配置做实时连接验证
- 最近一次巡检结果：GET /api/v1/admin/consistency-report
- 手动触发一次巡检：POST /api/v1/admin/consistency-check
- 系统可用检索路列表：GET /api/v1/admin/retrieval-paths

## 13. 部署架构与交付模式

### 13.1 单体化部署

系统采用单体 Docker 镜像部署，包含：

- FastAPI 应用（含 API 路由、页面路由、静态文件托管）
- 前端静态资源（CSS/JS）和 Jinja2 模板
- 框架核心包（`rag/` 目录）
- 客户适配器和配置文件（`customer/` 目录）
- 预下载的 Cross-Encoder 重排模型

这种打包方式使得整个系统对客户呈现为单一服务，降低运维复杂度。

### 13.2 外部依赖的部署边界

系统本体是无状态的（Session 状态外置到 Redis），所有存储依赖均为外部服务：

```
系统服务（Docker）
  ├── FastAPI 应用（无状态）
  │
外部依赖（客户自有或新建）
  ├── Redis             ← Session 状态缓存
  ├── Milvus/Qdrant     ← 向量存储
  ├── Elasticsearch     ← 全文索引
  ├── MySQL 		    ←  元数据库
  ├── MinIO/对象存储     ← 原文件存储
  ├── Neo4j/NebulaGraph ← 知识图谱（可选）
  ├── MySQL/PG（业务库）  ← 业务数据（可选，实时查询）
  └── LLM/Embedding     ← 模型推理服务
```

这一边界设计使框架容器本身可以水平扩展（多实例），所有状态都在外部存储中。

### 13.3 现场交付流程

完整的现场交付分为七个阶段：

1. **资源盘点**：梳理客户现有的存储、模型、认证基础设施，对照内置适配器清单确认对接方式

2. **配置文件编写**：填写 `customer_config.yaml`，配置各资源的连接信息和功能开关

3. **适配器开发**（视情况）：若客户使用框架未内置的服务，继承对应抽象基类实现适配器

4. **元数据库部署**：

   1. 执行建表 DDL（系统启动时自动执行，无需手工）
   2. 配置界面填写 MySQL 元数据库连接信息，测试连通
   3. 若客户有大量文档（>1GB），配置 `server_ingest_root`，使用服务器路径入库
   4. 配置通知方式（邮件/Webhook），告知客户管理员如何接收入库完成通知

5. **知识入库**：执行批量入库脚本，将客户文档写入知识库，确认 Chunk 数量和质量

6. **评测调优**：运行评测脚本，根据召回率和忠实度指标调整分块参数、同义词表和召回阈值

7. **上线部署**：构建 Docker 镜像，部署到客户的 Kubernetes 或虚拟机环境

8. **持续运维**：监控质量指标，迭代优化同义词表，处理新文档的增量入库

## 14. 性能特征与质量基准

### 14.1 延迟分解

从用户发送问题到开始接收流式回答，各阶段的时间消耗如下（P50 目标）：

| 阶段                  | 耗时目标   | 主要优化手段                        |
| --------------------- | ---------- | ----------------------------------- |
| 安全过滤 + 查询理解   | ~300ms     | 小模型（7B 量级）执行改写和意图分类 |
| 多路并行召回          | ~400ms     | 各路并发执行，5秒超时保护           |
| 融合 + 精排           | ~500ms     | Cross-Encoder 在 CPU 上批量推理     |
| Prompt 组装           | ~50ms      | 纯内存操作                          |
| 首 token 延迟（LLM）  | ~250ms     | 流式输出，边生成边推送              |
| **首 token 到达用户** | **< 1.5s** | 上述优化的综合结果                  |
| **完整答案（P50）**   | **< 5s**   | 取决于 LLM 生成速度                 |
| **完整答案（P95）**   | **< 10s**  | 各路超时控制                        |

元数据前置过滤步骤（MySQL 查询）增加约 10-50ms 延迟（有过滤条件时），无过滤条件时跳过（0ms）。

#### 入库性能

| 场景                        | 吞吐目标      | 说明                     |
| --------------------------- | ------------- | ------------------------ |
| 纯文字 PDF（100页）         | < 2 分钟      | 不含图片理解             |
| 含图片 PDF（100页，20张图） | < 8 分钟      | 含 VLM 图片理解（4并发） |
| 扫描型 PDF（100页）         | < 5 分钟      | OCR 处理                 |
| Excel（1万行）              | < 1 分钟      | 行列转文字描述           |
| 批量入库（100个文档）       | > 50文档/分钟 | 4并发，无 VLM            |

### 14.2 质量基准

| 指标                    | 目标值         | 含义                             |
| ----------------------- | -------------- | -------------------------------- |
| 召回覆盖率 Recall@20    | > 0.85         | 相关文档在 20 条召回中的覆盖比例 |
| 精排准确率 Precision@6  | > 0.70         | top-6 中与问题相关的比例         |
| 忠实度均值 Faithfulness | > 0.80         | 答案基于召回内容的比例           |
| 入库吞吐                | > 50 文档/分钟 | 批量并发入库（4 并发）           |

### 14.3 关键质量杠杆

从实践经验看，以下三个环节的投入对整体质量的边际收益最高：

**文档解析与元数据增强**（决定知识库质量上限）：准确的版面识别和高质量的摘要生成是后续一切的前提，垃圾进则垃圾出。投入 LLM 生成 Chunk 摘要和关键词的算力是值得的。

**查询改写与同义词扩展**（决定召回覆盖率）：维护一份准确的领域同义词表，配合多路改写，能显著提升 BM25 召回路的覆盖率，尤其是在专业术语密集的行业领域。

**Cross-Encoder 精排**（决定精度上限）：在粗排的基础上增加精排这一步，Precision@6 通常能提升 15-25 个百分点，是提升答案准确性最直接的手段。

### 15.1 关键数据流节点说明

**PipelineContext**是两条 Pipeline 的信息总线。每个步骤从 Context 读取上游结果，将本步骤的产出写回 Context，步骤之间通过 Context 传递而非直接调用。这一设计使步骤可以独立测试、独立禁用，且 Pipeline 引擎可以统一捕获每步耗时和错误。

**MemoryManager** 在问答 Pipeline 中被 QueryUnderstandingStep（读取 Session 历史）和 PromptAssemblyStep（读取三层记忆构造 Prompt）同步调用；在答案返回给用户后，记忆更新（写入短期记忆、触发摘要压缩）通过 `asyncio.create_task` 异步执行，不增加用户等待时间。

**AdapterRegistry** 在系统启动时完成一次性的适配器实例化，之后在整个生命周期内保持单例，Pipeline 步骤在构造时注入具体的适配器实例，运行时无需再查找注册中心。

**DAG Pipeline 引擎**在执行每个步骤前检查整体超时（默认 30 秒），步骤失败时将错误写入 Context 的 errors 列表，根据配置的 stop_on_error 决定是否继续执行后续步骤。若 Context 中已存在答案（如安全过滤直接返回了拒答内容），引擎跳过所有检索和生成步骤，直接执行后处理步骤（如格式化输出）。

**YAML WorkflowRegistry**（写侧核心）：声明式定义各文档类型的处理步骤。`detect_format`（magic bytes）是所有 workflow 的第一步，防止格式伪装。条件分支步骤（`condition_pdf_route`）在运行时动态决定后续步骤序列。

**QueryPlan**（读侧核心）：将用户问题结构化为五个层次（约束/实体/关键词/语义/同义词），各层独立投放到对应检索路，互不干扰。`active_paths` 由 `route` 权重（浮点）动态计算，而非布尔开关。

**EntityLinker**：在 QueryUnderstandingStep 内部运行，将查询实体链接到知识库规范名，使 kw_exact 精确路能命中正确文档。两阶段实现（规则→向量），规则阶段毫秒级，不影响主链路延迟。

**SelfEvalStep**：位于 RRFFusion 和 CrossEncoderRerank 之间，评估当前融合结果质量，不足时触发第二轮（改写+HyDE），合并结果后再精排。最多 2 轮，普通查询零开销直通。

**IngestBatch**：所有入库操作（UI上传/本地目录/服务器路径）统一创建批次，子任务挂在批次下。UI 提供批次视图（聚合进度）和任务视图（每文件详情）两级切换。

**make_chunk_id**（替代 uuid4）：确定性哈希生成，同位置同内容的 Chunk id 不变，文档重新入库时 ES/Milvus upsert 精确覆盖，无孤立旧数据，大幅简化一致性保障逻辑。
